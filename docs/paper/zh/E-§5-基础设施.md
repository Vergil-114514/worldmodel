# 5 基础设施

本节描述为支撑 Cosmos 3 端到端生命周期而设计的一体化基础设施栈。如图 11 所示，平台统一了 4 大核心支柱：

- • *数据工程。* 接入原始多模态数据，并将其转换为 WebDataset 格式的精选数据集，针对可扩展的分布式训练进行优化。

- • *大规模训练。* 通过高度高效的并行化策略、优化的数据加载、快速的 checkpoint 保存以及集合通信原语，最大化 NVIDIA GPU 集群利用率。

- • *模型服务。* 在生成式与推理式两类工作负载上实现高效、低延迟的部署与推理执行。

- • *基准测试与验证。* 提供统一的评估框架，在多样任务上评估模型能力，支持自动化的回归跟踪与系统化的模型比较。

## 5.1 数据基础设施

Cosmos 3 的训练语料取自数百亿（tens of billions）图像与视频候选，横跨多样的模态、领域与任务。在这一规模上运转，要求数据基础设施同时具备三种能力：(1) 通过大规模分布式处理把原始多模态数据转化为可训练样本；(2) 支持基于嵌入的检索、聚类与去重；(3) 支持交互式的数据集可视化、检查与调试。为满足这些需求，我们开发了 **SILA**（Scalable Infrastructure for Large-scale data processing and Annotation），一个可扩展的多模态数据基础设施平台，它把存储、元数据管理、分布式处理、语义检索与数据集可视化整合进单一可扩展框架，用于大规模数据整理与管理。

SILA 围绕“流水线逻辑与基础设施机制的清晰分离”构建。研究者声明带类型的处理阶段——指定每个阶段所消费的列与其所产出的输出——而平台透明地处理数据集分片、分布式执行、容错、checkpoint、元数据更新与资产注册。这一抽象使得引入新的数据源、基础模型与处理阶段（包括过滤、caption 生成、嵌入生成、打分与打标）变得简单直白，无须研究者具备分布式系统的专业知识。由此带来的结果是：平台让数据整理能够以研究本身的节奏演进——随着模型、质量标准与训练配方的变化，新信号可以增量地被加入、重算或替换。

### 5.1.1 大规模数据处理

多模态数据整理是一个迭代式的富集（enrichment）过程，而非一次性的离线预处理。随着模型、质量标准、标签与训练配方的演化，原始的文本、图像与视频样本被反复变换、过滤、标注与再处理。扩展这一工作流很有挑战，因为该流水线既低产出又高度迭代：只有很小比例的原始候选最终存活并进入训练，这意味着低效的扫描、拷贝或模型推理被不成比例地花在了后续会被丢弃的样本上。同时，接入（ingestion）、切分与转码、嵌入生成、去重、过滤、分类体系打标、caption 生成、分片等阶段要对同批样本反复操作。因此，支撑这一工作流需要针对数十亿多模态样本的高效机制，以完成重复变换与增量重算。

这些挑战在分布式执行下更加突出。整理工作负载必须在共享集群上持续运行，而集群中的 GPU 可用性是碎片化且动态变化的，不能假设存在单一的整体式配额。基础设施必须协调大量分布式 worker、避免重复计算、从故障中恢复、管理 CPU 密集与 GPU 密集混合的各类阶段，并在资源出现时继续处理未完成的工作。为支持这一执行模型，SILA 结合了：统一数据层、fragment 级协调与故障恢复、分阶段分布式执行、节点内模型服务端点、机会式的集群利用，以及对 agent 友好的运维接口。

#### 统一数据层。

SILA 把数据整理组织为一个统一的列式 Lance 数据集（Pace et al., 2025）：每一行代表一个数据样本，每一个带类型的列代表一个整理信号，例如 caption、标签、质量分数或标注。这取代了早期基础设施——Cosmos-Predict 1.0（NVIDIA, 2025a）与 2.5（NVIDIA, 2025b）——所使用的“每流水线一张表”架构：在那套架构中，每条流水线写入自己的 Postgres 表，输出随后通过变更数据捕获（Change Data Capture, CDC）同步进 Databricks。随着流水线数量与元数据字段数量增长，“每流水线一张表”的设计需要跨大表进行日益复杂的 join 才能重建单个样本的状态。这些 join 在大规模下代价高昂，即使简单的运维查询，若不详细了解 join 键、表关系与流水线专属模式也难以表达。相比之下，SILA 通过在共享 Lance 表上追加新的带类型列，对同一逻辑样本进行增量富集。这一统一表示天然契合多模态整理工作负载——多数阶段是对既有样本追加额外元数据，而非创建新实体。通过把数据集内容、元数据与处理状态共置一处，系统能够高效支持大规模扫描、点查、增量重算，并直接从 Lance fragment 元数据发现未完成的工作，而无须昂贵的启动期 join。

#### Fragment 级协调与故障恢复。

这一规模下的整理以高并发运行：单个作业内的许多分布式 worker，以及许多并行运行的独立作业，都在对同一份持续演化的 Lance 数据集进行读写。若没有显式协调，worker 只能依赖昂贵的启动查询、随机采样，或事后过滤已处理样本来避免重叠。这些做法会延迟作业启动、允许重复工作，并使长时间运行的作业被抢占或中断后的恢复变得复杂。SILA 改为直接在 Lance-fragment 层面协调分布式整理。worker 从 Lance 元数据中发现未完成的 fragment，并在处理它们之前获取有时限的租约（lease），而 Lance 数据集本身仍是完成状态的事实来源。租约所有权通过周期性心跳维持；心跳停止时租约到期，另一个 worker 可以重新获取该 fragment，从而对故障、抢占或端点崩溃实现自动恢复，无须人工清理。由于单个 fragment 可能包含许多样本并需要数小时的模型推理，SILA 进一步把已认领的 fragment 划分为更小的处理段（segment），将完成的段作为持久 checkpoint 写出，待全部段完成后，通过一次元数据更新将整个 fragment 原子地提交回 Lance。这把恢复单元与可见性单元解耦：中断的作业从已完成的段继续执行，而下游读取者只看到完全提交的 fragment 输出。

#### 分阶段 Ray 执行。

整理流水线混合了资源画像差异极大的异构操作，包括数据加载、解码、模型推理、后处理、写出与提交。若这些操作通过一个单一、无差别的控制循环执行，快速的上游阶段会堆积中间输出，而较慢的推理或提交阶段会成为瓶颈。SILA 改为通过分阶段的 Ray 流水线引擎（Moritz et al., 2018）执行每个已认领的 fragment。由框架管理的阶段负责加载、写出与提交；用户定义的 preprocess、compute 与 postprocess 阶段则在各自独立的 Ray actor 池中执行，并分别独立配置 worker 数量与资源需求。背压（backpressure）上限限制跨阶段边界的在制品数量，防止快速的 I/O 密集阶段压垮较慢的下游阶段，并迫使 Ray 对象存储溢出到磁盘。

#### 节点内模型端点。

基础模型整理工作负载往往需要在许多流水线 worker 并发处理数据的同时，服务大规模的 caption、嵌入、打标或打分模型。集中式推理服务在大规模下可能成为瓶颈，而要求一大块连续的 GPU 配额又会削弱利用集群碎片化可用资源的能力。SILA 转而使用 vLLM（Kwon et al., 2023）等系统启动节点内的模型服务端点，并把本地端点信息直接传给各阶段 worker。worker 随即调用节点内服务进行推理，使模型密集的整理阶段能够跨可用节点扩展，并将数据并行的流水线执行与模型服务的放置位置解耦。

#### 机会式的集群利用。

大规模整理必须与训练工作负载在共享集群上并行持续运行，而集群的 GPU 可用性往往碎片化且动态变化。SILA 不要求单一的整体式配额，而是把整理分解为细粒度的分布式作业，可随资源出现而增量执行。系统支持 DGX Cloud Lepton（NVIDIA, 2026c）与 Slurm（Jette and Wickberg, 2023）等执行后端，让流水线机会性地利用空闲或仅部分可用的 GPU 容量。这提升了集群利用率，并使持续的数据处理无须大块连续的 GPU 预留。

#### 智能体化（agentic）作业编排。

随着 AI agent 在工具使用与长时程执行方面的能力不断增强，SILA 通过对 agent 友好的运维接口暴露大规模整理工作流，包括可复用的技能、命令行接口（CLI）与结构化作业元数据。长时间运行的编排 agent 周期性地监控整理作业、检查日志与执行元数据、重启失败的阶段，并自动协调运维恢复。通过这一持续监控循环，agent 可以跟踪流水线进度、识别停滞或不健康的 worker、核验数据集覆盖情况、在新模型或新过滤标准引入时触发增量重算，并在分布式作业不断演化的过程中就故障、恢复与执行状态通知工程师。

这些设计选择共同显著提升了大规模整理的效率。通过消除昂贵的启动期表 join，并用 fragment 级的发现与协调取代随机化的工作选取，SILA 把作业启动延迟从 30–60 分钟降至约 5 分钟，具体取决于阶段与模型配置。结合分阶段执行、checkpoint 与集群利用率改善，新基础设施相对先前架构实现了 $10\times$ 的吞吐量提升。在生产高峰时段，单个 SILA 阶段每天处理数十亿行级标注，把大规模的 caption 与整理活动从月级操作缩短为周级的迭代周期。

除了提升可扩展性与吞吐量，SILA 还把大量运维复杂性隐藏在以数据集为中心的接口之后，从而简化流水线开发。流水线作者只需声明其消费的输入列与产出的输出字段，框架便负责模式注册、列创建、fragment 发现、工作协调、checkpoint，以及把结果提交回共享数据集。因此，新增 caption、打分、打标或过滤阶段不再需要创建新的存储表、编写同步逻辑或手工协调分布式 worker。研究者转而可以通过增量地添加新的带类型列、复用先前已计算好的输出，并仅对缺失必需字段的样本进行重算来持续迭代。

### 5.1.2 嵌入存储与语义检索

语义检索工作负载要求在数十亿条多模态数据上同时进行向量相似度搜索与元数据感知过滤。在先前的架构中，把高维嵌入直接存于 SQL 表会显著膨胀表体积，增加 join、扫描与运维查询的 I/O 开销。因此，嵌入被导出到独立的向量数据库，而用于前过滤、后过滤与结果解读的元数据仍留在关系型存储中。然而，嵌入、元数据与过滤标准在整理期间持续演化：只要引入新的嵌入模型、元数据字段或搜索过滤器，就需要在两套系统之间频繁同步与迁移。

SILA 转而把嵌入直接连同样本元数据一起存储在 Lance 中，使 LanceDB 能够在主数据集之上构建向量索引，而无须单独的向量数据库（LanceDB, 2026）。由于嵌入存于 Lance 数据文件而非内联在关系行中，大体积嵌入载荷不会膨胀元数据表或拖慢运维查询。通过把嵌入、元数据与向量索引共置于同一存储层，SILA 可以直接在整理后的数据集上支持语义检索、聚类与去重，同时保持检索结果与最新整理状态一致。

在生产环境中，SILA 在一个覆盖数百亿行的 4096 维嵌入列上执行语义检索、聚类与去重，使用带余弦相似度的 LanceDB IVF_PQ 索引。所部署的近似最近邻（Approximate Nearest Neighbor, ANN）配置采用 64K 个 IVF 分区，并配合 PQ 压缩嵌入，以高效支撑十亿级的检索工作负载。由于向量索引直接构建于主 Lance 数据集之上，语义检索得以在与维护最新整理元数据和过滤状态的同一存储层上运作。这使得元数据感知过滤、最近邻检索与下游数据集分析能够与持续演化的嵌入、标注及整理输出保持同步，而无须在相互独立的向量系统与元数据系统之间做同步。

### 5.1.3 数据集可视化、检查与调试

在生产规模下，数据整理不仅要可扩展，还要可观测：研究者需要理解流水线的覆盖情况、跟踪整理输出随时间的演化，并诊断单个样本为何通过或未通过质量标准。因此 SILA 把可视化、检查与调试视为数据基础设施的一等组件。其工具直接在 Lance 表上运作，把汇总级的流水线进度、有代表性的开发子集、样本级检查与下游分析视图连接在同一共享整理基底之中。

- • *开发与流水线验证。* SILA 提供工具，用于从生产数据集构造小型开发用 Lance 表，同时保留全量语料的模式与有代表性的运维特征。由于这些开发表与生产数据高度相似，同一流水线可以在两种环境中不加修改地运行，使研究者在启动大规模生产作业之前即可验证正确性与执行行为。

- • *数据集检查与进度分析。* 为支撑大规模整理监控，SILA 直接在 Lance 表上暴露汇总进度分析器与交互式检查工具。fragment 级元数据用于估计逐列覆盖率与流水线完成度，而无需全表扫描；交互式查看器允许研究者采样行、渲染媒体，并检查相关的 caption、分数、标注与模式元数据。由于 Lance 支持高效的行级随机访问，这些检查工作流可以直接作用于主整理表，避免了传统基于 Parquet 的数据湖中常见的昂贵扫描与受限的行级检索模式。这使研究者能够在同一数据集内从流水线级的进度监控迅速推进到样本级的调试。

- • *分析查询集成。* 对于大型分析负载，SILA 支持联机分析处理（Online Analytical Processing, OLAP）查询，用于对整理后的语料进行大规模聚合、报表与仪表盘展示。这些查询更易表达，因为 SILA 把每个样本及其整理信号存放在一张宽 Lance 表中：caption、标签、分数、嵌入、过滤决策与处理状态都可以从单一逻辑数据集中选取与过滤，而无须跨多条流水线专属表重建。选定相关的列与样本群后，分析后端即可计算覆盖报告、质量仪表盘、数据集审计与训练集分析所需的聚合。SILA 将 Lance 表保留为整理状态、媒体、元数据、嵌入、向量索引与行级检查的事实来源，而把下游分析执行视为一种部署选择。实践中，SILA 可以扫描权威的 Lance 表以物化出可查询的快照或投影，其中包括 Parquet 文件（Le Dem, 2013），并使用可用的计算后端执行 OLAP 负载，例如 Databricks、Spark 集群（Zaharia et al., 2016）或由 Slurm 支撑的批处理作业。

贯穿处理、检索与检查，SILA 闭合了定义 Cosmos 3 数据基础设施的三大目标的循环：把原始多模态语料转化为可训练样本、为语义检索与去重加以组织，并在整个整理生命周期内保持可检查。通过在单一 Lance 支撑的基底中统一资产、整理信号、嵌入、向量索引与执行状态，SILA 把数据整理从一连串一次性的预处理作业转变为持续演进的生产工作流。新模型与质量标准可以增量地应用；分布式富集阶段可以在共享的异构集群上恢复并扩展；研究者可以在语料级的进度监控与样本级的调试之间无缝切换。这一体化工作流使 Cosmos 3 训练语料能够扩展至数百亿多模态候选，同时保持可检索、可审计与持续可改进。

## 5.2 训练基础设施

Cosmos 3 依托一个为扩展多模态基础模型训练而专门打造的定制基础设施平台。这一统一栈协调 Reasoner 与 Generator 训练的端到端生命周期。该生命周期覆盖原始多模态样本接入、训练计算与持久 checkpoint 保存，并围绕下述阶段组织。

- • *数据加载器。* 数据加载器以任意原生分辨率与宽高比接入多模态样本——图像、视频、动作、音频、文本。它即时（on-the-fly）施加增强（例如缩放、空间裁剪、颜色抖动与视频时间下采样），对文本条件做 tokenize，并把变长样本打包成批次。为隐藏 I/O 与预处理延迟，加载器在并行的 worker 进程中异步运行，并通过锁页内存（pinned-memory）中转缓冲把批次预取到设备上。

- • *分布式训练。* 训练采用混合分片数据并行（Hybrid Sharded Data Parallelism, HSDP）与上下文并行（Context Parallelism, CP）的组合进行并行化。这一方法能够扩展到大模型尺寸与超长的输入序列长度。HSDP 在每个副本组内分片优化器状态、梯度与模型参数，并在组之间复制。CP 则沿序列维度把数据分片到各设备，以处理否则将溢出单块 GPU 显存容量的超大上下文窗口。这两种策略正交组合，并按实验动态配置，以针对目标模型尺寸、序列长度与集群拓扑进行优化。

- • *训练循环。* 训练循环按 TorchTitan（Liang et al., 2024b）的风格编排，执行标准的前向、反向、优化与学习率调度周期。它原生支持多种优化器（例如 AdamW 及其融合变体）、调度器（例如带 warm-up 的余弦、带 warm-up 的常数）与损失函数（Reasoner 文本用交叉熵损失，Generator 用 EDM 损失）。流水线还接入即时的变分编码器（例如 Wan2.2 VAE），从而在原始多模态输入上端到端运行。这一设计消除了离线的隐变量提取阶段，并确保增强、编码与训练在各次运行之间保持步调一致。

- • *Checkpoint 保存。* Checkpoint 以可配置的节奏记录，并使用异步、脱离关键路径的持久化机制，防止磁盘与网络 I/O 使训练循环停滞。模型参数、优化器状态以及 RNG/数据加载器状态在设备上快照，交接给后台写入进程，并在训练不中断地继续运行的同时序列化到远端存储。

Reasoner 与 Generator 都使用这一统一框架训练，共享同一个 trainer、并行化架构、优化器、学习率调度器、tokenizer、数据加载器与监控工具。

### 5.2.1 数据加载器

数据加载器连接持久存储与训练循环：它接入原始多模态训练数据，即时施加增强，并组成每个训练步所消费的批次。在 Cosmos 3 中，数据加载器被要求同时满足三项并行要求：

- • *流水线饱和。* 它必须异步流式供给批次，防止训练循环在数据 I/O 上停滞或阻塞。

- • *分布式负载均衡。* 它必须在分布式 rank 之间发出均衡的批次，以最大限度减少跨 rank 的同步停滞，并最大化整体 GPU 利用率。

- • *分布保真。* 它必须保证长期的模态与分辨率混合严格贴合所配置的目标分布。

在传统 LLM 训练中，这三项要求都有成熟的解决办法。

- • *流水线饱和。* 这通过调节 worker 数量与预取深度，并使用锁页内存中转缓冲来重叠主存到设备（host-to-device）的传输与计算实现。

- • *负载均衡。* 这变得轻而易举，因为每个样本贡献固定数量的 token。保持各 rank 相同的样本数即可保证各 rank 统一的计算量与激活显存画像。

然而，Cosmos 3 使这套配方在全部三个维度上失效。由于其联合训练语料横跨高度异构的模态，单样本 token 数相差超过两个数量级，使得 token 量成为计算与显存开销的首要驱动。例如，单个 720p 两秒视频片段产生的 token 比数十条短文本 caption 加起来还多。在这种不对称负载下，给各 rank 分配相等的样本数会引入严重的系统性低效：它造成 (a) 固定批次形状带来的大量 padding 浪费；(b) 当各 rank 的模态分配不同时产生严重的负载不均；(c) 在大规模下，极端的步时方差引发 NCCL 集合通信超时。

为应对这些挑战，Cosmos 3 数据加载器围绕四项协同机制构建：(i) *token 预算打包序列*，以 token 预算而非固定样本数约束每个 rank 的单步负载；(ii) *联合数据加载器*，把各数据流的加载器多路复用为单一统一的训练批次；(iii) *rank 同步的流选择*，使用全局播种的选择器使所有 rank 在每一步对齐到同一数据流；以及 (iv) *前瞻打包*，提高 token 预算 $T_{\max}$ 的平均利用率。

#### Token 预算打包序列。

每个 rank 的单步负载不以固定的样本数约束，而以严格的 token 预算 $T_{\max}$ 约束。加载器贪婪地把样本串接成单一打包序列——每个样本恰好贡献其序列化形式所需的 token，样本之间不插入 padding——直到追加下一个候选会超出 $T_{\max}$ 为止。通过消除跨样本 padding，这一设计把单步计算成本约束为 $T_{\max}$ 的直接且可预测的函数，使硬件免受波动的模态组合所引入的执行方差影响。作为防御性的次级约束，单步样本数同时也封顶于 $N_{\max}$。

#### 联合数据加载器。

每个模态、数据集或更细粒度的数据流都封装在其自己的加载器中，配备私有预取缓冲以隐藏存储延迟。*联合数据加载器*（如图 12 所示）在这些各流加载器之间多路复用，每步组装出单一统一的训练批次，同时完整保留各流的缓冲、预取与可观测性。

![Figure 12](figures/joint_dataloader.svg)

> Figure 12: **联合数据加载器总览。各流专用数据加载器为每个 rank 上的本地分流缓冲供数。在每个全局迭代，一个 rank 同步的选择器在分布式 rank 之间选择同一个流 $k_{i}$。随后每个 rank 从其选定的本地缓冲中，在 token 与样本数预算之下贪婪地打包样本组成 $B_{i}^{(\rho)}$，并利用有界前瞻减少未使用的 token 容量。**

#### Rank 同步的流选择。

基础模型训练通常从同时包含图像与多种空间分辨率视频的数据集中取样。各流之间的单样本 token 数相差数量级。例如，视频样本往往携带比图像多 $100\times$ 以上的 token，而 720p 视频又比 256p 视频多 $10\times$ 以上。若允许每个 rank 独立选择其流，在 FSDP 下会造成严重的工作负载不均——同一步之内各 rank 的注意力 FLOPs（因其二次复杂度）差异悬殊。我们通过一个以迭代索引为键、全局播种的选择器来选定活动流，从而缓解这一问题，确保所有 rank 在每一步都处理来自同一模态与分辨率桶的样本。这消除了跨 rank 的计算时间与激活显存方差，而确定性的、由种子导出的选择序列在 checkpoint 与重启之间可比特级精确复现。相比无同步的基线，rank 同步流选择将端到端训练吞吐量提升 $54\%$。

#### 前瞻打包。

给定迭代 $i$ 选定的流 $k_{i}$，联合数据加载器贪婪地构建本地批次：从该流缓冲的头部依次追加样本，直到下一个候选会超出 token 预算 $\mathbb{T}_{\max}$。然而，纯贪心打包会在下一候选大到足以溢出、但缓冲更深处仍有更小候选可用时，留下相当比例的预算未被利用——这部分残余容量在功能上等价于 padding，并与吞吐损失成正比。我们用有界前瞻策略来解决这一问题。当某候选样本超出*总*token 预算 $\mathbb{T}_{\max}$ 时，该样本在当前配置下不可打包，将其丢弃（并记录一条警告）。当候选仅超出*剩余*预算、而批次已经非空时，该候选被临时移入一个*旁路缓冲（look-aside buffer）*，加载器继续向流缓冲更深处扫描，寻找能够填满残余容量的更小样本。

该机制如图 13 所示。在该示例中，样本 $a_{1}$ 与 $a_{2}$ 可以放入当前批次；$a_{3}$ 超出剩余预算，被转入旁路缓冲；随后加载器继续扫描并打包后续更小的样本，例如 $a_{4}$ 与 $a_{6}$。在迭代结束时，旁路缓冲中剩余的所有样本按其原始到达顺序被放回流缓冲的头部，因此前瞻能在不永久重排该流的前提下减少 padding。为约束病态情形（例如某流暂时被超大样本主导）的代价，每次迭代的连续前瞻尝试次数受一个可配置的每流上限约束。在生产中我们取上限为十；超过该值后，我们观察到未使用容量的额外缩减微乎其微，而旁路缓冲的大小（及其内存占用）却持续增长。总体而言，相比基线，前瞻打包把有效序列长度提升 $8\%$，带来训练吞吐量的相应改善。

> Figure 13: **联合数据加载器中的前瞻打包。加载器从选定流贪婪扫描样本，把能够放入剩余 token 预算的样本打包进当前 mini-batch（Mint）。超出预算的样本被临时置入 look-aside 缓冲（Rose），从而让后续更小的样本填充剩余容量。在迭代结束时，被跳过的样本按其原始到达顺序返回流缓冲头部，从而在减少 padding 的同时跨迭代保持流顺序。**

#### 冷启动处理。

我们的若干数据流会承受很高的首批（first-batch）延迟，主要来源是 worker 进程派生、为新打开的分片所做的文件系统元数据缓存，以及流专属的反序列化预热。若这笔延迟要到第一个训练步才支付，它就会与该步上的 NCCL 集合通信“赛跑”，并有很大概率在最慢的 rank 上触发看门狗（watchdog）超时——在大规模下尤其如此，因为此时起决定作用的是跨 rank 的最大值。为消除这一失效模式，联合数据加载器在构造期间执行一个显式的预热阶段：它从每个流各取回一个批次，使 worker 池、文件句柄与反序列化缓存全部预热完毕，随后发出一个分布式 barrier，再把控制权交还训练循环。这保证每个 rank 在第一次前向之前都已支付冷启动成本，且第一个迭代面对的是完全预热的流。

#### 可观测性与集成。

在每个迭代，联合数据加载器向训练侧的监控回调发出一条结构化的打包统计记录；该回调跨分布式组聚合各 rank 的记录，并把结果记录到 Weights & Biases。上报的指标包括：各流的实测采样比例（与配置的目标混合进行对比）、每迭代打包的样本数、各流缓冲的占用率与等待时间、前瞻饱和率，以及每迭代的 token 预算利用率。这些指标暴露出那些最可能在大规模训练中“不崩溃但悄悄劣化”的失效模式，使此类问题在出现后数分钟内即反映在训练仪表盘上，而不是日后从模型行为中才被发现。

### 5.2.2 注意力实现

如第 2.3.1 节所述，Cosmos 3 中的 Mixture-of-Transformers 架构要求两种迥异的注意力需求在同一次前向传播中并存：Reasoner 通路仅对 Reasoner token 施以因果注意力，而 Generator 通路则对 Reasoner 与 Generator token 的拼接施以双向注意力，从而让每个 Generator token 能够以完整上下文为条件。用 FlexAttention 这类通用算子朴素地表达这些异构掩码模式，结果虽正确，但硬件利用不足：掩码结构对内核而言是不透明的，而在本应被跳过的注意力块内仍执行了等价于 padding 的工作。这降低了张量核心（tensor-core）利用率并加剧了内存带宽压力。

为解决这一问题，我们协同设计了一种自定义的双向扁平注意力（two-way flat attention）机制，把跨通路的掩码结构直接暴露给高性能的变长注意力内核。图 14 说明了该设计。计算被分解为两次独立的内核调用。第一次处理 Reasoner 通路，是一个仅作用于 Reasoner 查询、键与值的标准变长缩放点积注意力（scaled dot-product attention, SDPA）（PyTorch Contributors, 2026b）带因果掩码调用。第二次处理 Generator 通路，它要求在同一样本内，Reasoner 与 Generator 的 key/value 流对每个 Generator 查询都可见，但在打包批次的不同样本之间严格隔离。我们通过以样本为粒度把两条 token 流按如下顺序扁平化并交错来实现这一点

$$[R_{0},G_{0},R_{1},G_{1},\ldots,R_{n},G_{n}]$$

其中 $R_{i}$ 与 $G_{i}$ 分别表示样本 $i$ 的 Reasoner 与 Generator key/value token。每个 Generator 查询在其自身样本的 $[R_{i},G_{i}]$ 块上双向注意。这一表述以每层两次变长内核启动表达完整的跨通路注意力，在同一个打包表示内同时支持因果与双向掩码，消除了固定长度实现所固有的 padding 开销，并相对基于 FlexAttention 的基线为 Cosmos3-Nano 模型带来 $22\%$ 的端到端训练吞吐提升。

![Figure 14](figures/tikz_two_way_attention.svg)

> Figure 14: **双向扁平注意力。每条通路实现为单次变长 SDPA 调用。(a) Reasoner 通路在打包的 Reasoner token 上使用标准的因果 varlen 调用，产生块对角的因果掩码。(b) Generator 通路将 Generator 查询与交错的 key/value 流 $[R_{0},G_{0},R_{1},G_{1},\ldots,R_{n},G_{n}]$ 分开打包。所得掩码是块对角的，但每个块内部为矩形，使得每个 Generator 查询在其自身样本的 $[R_{i},G_{i}]$ 上下文上双向注意而不跨越样本边界。该示例使用三个打包样本，$(|R_{i}|,|G_{i}|)=(3,2),\,(2,3),\,(4,1)$。**

变长注意力后端按平台选择，以匹配目标硬件上性能最佳且经过数值验证的实现。在 Hopper 级 GPU（H100、H200）上，我们使用 FlashAttention-3（Shah et al., 2024），它利用 Hopper 架构的 WGMMA 指令与基于 TMA 的异步数据移动，提供接近峰值的注意力吞吐。在 Blackwell 级 GPU（GB200）上，我们使用 NATTEN（Hassani et al., 2023），其变长内核基于 CUTLASS 模板库构建，并专为 Blackwell（SM100/SM103）的第五代张量核心与更新后的内存层级调优。两个后端都经由统一的分派接口访问，因此内核的选择对训练栈的其余部分是透明的，并可随新后端成熟而重新评估。

### 5.2.3 分布式训练

Cosmos 3 的 Reasoner 与 Generator 分别使用一套分布式训练栈进行训练，该栈把混合分片数据并行（HSDP）与上下文并行（CP）相结合。HSDP 在每个副本组内分片模型参数、梯度与优化器状态，并在组之间复制，这以少量组内通信换取了在单卡显存预算有限的商用 per-GPU 内存预算上训练数十亿参数模型所需的显存余量。相比之下，CP 针对另一类瓶颈：单序列激活显存，它随上下文长度线性增长，否则会对可训练序列规模形成硬性上限。两种策略正交组合，而 (HSDP-degree, CP-degree) 配置按实验选定，以匹配目标模型尺寸、序列长度与集群拓扑。

#### 通过 Ulysses 方案实现上下文并行。

对于 CP，我们采用 Ulysses 方案（Jacobs et al., 2023），它在注意力之外沿 token 维把输入序列切分至各 CP-rank 设备，并在每个注意力层中使用两次 all-to-all 集合通信来切换分片轴。第一次集合通信把 Q/K/V 激活从序列维重新分布到注意力头维，使每个 rank 持有一组互不相交的 head 的完整序列，从而可以在本地执行注意力而无需进一步的跨 rank 通信；第二次集合通信在注意力输出上恢复原有的序列分片布局。

该方案与序列打包（sequence packing，见第 5.2.1 节）以及双向注意力机制集成得很干净。为双向注意力操作而对 Reasoner 与 Generator key/value 流所做的扁平化与交错被推迟到 head 轴重分布之后进行——此时每个 rank 已持有其被分配 head 的完整序列，可以在本地完成拼接。因此同一套变长注意力内核在 CP 中原样复用，无须 CP 专属的内核变体。此实现所支持的最大 CP 度受限于模型中的查询头数——Cosmos3-Nano 为 32，Cosmos3-Super 为 64——鉴于 Cosmos 3 所针对的上下文长度与单 GPU 显存预算，我们在实践中发现这一限制并不构成约束。

#### 为何不用环状注意力？

我们考虑过以环状注意力（ring attention）实现 CP 这一替代方案，但在我们的设定下发现其吸引力明显不足。Ring attention 需要先把包含交错排布的 Reasoner 与 Generator token 的单一打包序列物化出来，再跨 CP rank 对其进行分片，以便向环形调度暴露连续的 K/V 流。这排除了 Ulysses 天然允许的两条通路独立分片，并使在轮换的环形调度下构造逐样本的双向/因果掩码变得复杂。再加上 all-to-all 在 NVLink 互联节点上有利的带宽表现，这些因素促使我们选择 Ulysses 作为 Cosmos 3 的 CP 策略。

### 5.2.4 选择性激活重计算

计算 Transformer 的反向传播需要前向传播期间产生的中间激活可用，但在 Cosmos 3 所针对的模型规模与上下文长度下，同时物化全部激活的显存代价不可承受。标准的缓解手段是激活重计算（activation checkpointing）（Chen et al., 2016）：前向只存储一小集“锚点”激活而丢弃其余部分，被丢弃的张量在反向期间通过从最近的已保存锚点重跑相应的前向子图来重新计算。默认策略只保存每个 Transformer 块的输入，并按需重算块内的一切；这把激活显存降到最低，却在反向期间引入一次额外的前向传播，使单步 FLOPs 增大约 $33\%$，端到端训练吞吐也相应下降。

为在激活显存预算之内降低这一重分开销，我们应用选择性激活重计算（selective activation checkpointing, SAC），即把一小部分精选的中间张量额外保留在内存中而不予重算。选择遵循一条简单的成本-收益启发式：按各操作的 FLOPs-对-内存比排序候选——即每提交一字节激活显存所省下的重算代价——并优先物化比值最高者，直到激活显存预算耗尽为止。对 Cosmos 3 而言，注意力输出是该策略迄今最主要的受益者：注意力的重算代价高昂，因为其成本随序列长度二次增长；而注意力输出张量本身相对较小（随序列长度与隐藏维度线性增长），这使它成为 FLOPs-对-内存比最高的操作。用户还可以通过针对操作名的正则表达式模式配置自定义保存集合，我们在残余激活显存余量允许时用它保留少量次级张量。

在我们的测量中，对 Cosmos3-Nano 应用“物化注意力输出”的 SAC，在单批次 token 预算为 $74{,}000$ 时带来 $13\%$ 的端到端训练吞吐提升，且数值结果没有任何变化。

### 5.2.5 用于 Transformer 块的 torch compile

我们在整张训练图上应用 torch.compile，设置 fullgraph=True 与 dynamic=True。fullgraph 模式消除 CPU 开销并启用算子融合（operator fusion），而 dynamic=True 处理由混合模态批次产生的可变序列长度——例如在各迭代之间，Generator 通路的 token 远长于图像批次的 token。Torch compile 为 Cosmos3-Nano 的 Generator 训练带来 $41\%$ 的训练吞吐提升。

### 5.2.6 视频 tokenizer

Cosmos 3 训练要求解码后的视频帧由视频 VAE 即时 tokenize 为隐变量表示：在我们的配置中是 Wan2.2（Wan et al., 2025b）。在最初的实现中，我们观察到该 tokenizer 在每个训练步中占据不成比例的比例——对较小的 Cosmos3-Edge 与 Cosmos3-Nano 模型甚至主导了整个前向传播。在这类模型中，Transformer 计算足够小，VAE 无法被该步的其余部分摊薄。由于 tokenizer 位于数据加载器与训练循环之间的关键路径上，它引入的任何延迟都会直接侵蚀训练吞吐。为此我们实现了一系列针对性优化，它们合起来显著降低了 tokenizer 的墙钟时间贡献。

#### 分块编码。

Wan2.2 因果 tokenizer 先编码一个 1 帧的“prime”块，随后每个隐变量块对应 4 个像素帧；默认的每次调用粒度为一个隐变量块（即 prime 之后每次 4 帧）。这一默认设置在训练所使用的空间分辨率下让 GPU 严重欠利用，因为每次内核启动的工作量太小，无法让张量核心饱和。我们改为按可配置的每调用像素帧数调用编码器，以额外的激活显存换取每次启动更高的算术强度（arithmetic intensity）。最优块大小取决于分辨率。在较高的空间分辨率下，每帧本身已消耗大量显存，因此在触发 OOM 之前每次可容纳的帧数更少；而在较低分辨率下，大得多的块既可行又有益。我们在训练硬件上经验确定了以下工作点：256p 用 68 帧，480p 用 24 帧，720p 用 12 帧。这些配置把编码器推到 roofline 曲线的计算受限一侧，同时远低于单 GPU 显存预算，贡献了单步加速的主体。

#### 提前编译。

> Figure 15: **Wan2.2 tokenizer 的分片式提前编译。由 $\{3\text{ resolutions}\}\times\{5\text{ aspect ratios}\}\times\{3\text{ tokenizer call modes}\}$ 产生的 $45$ 张静态形状图被划分到各 rank；每个 rank 对其被分配的图执行编译，把编译产物写入共享文件系统，并在训练开始前加载全部产物。预热时间从 $\sim\!15$ 分钟（串行）降至 $<\!1$ 分钟（分片）。**

在分块编码之上，我们对 tokenizer 使用 torch.compile：通过融合逐点（pointwise）操作并为编码器的卷积与注意力块选取优化后的内核调度，它额外带来 $52\%$ 的编码延迟下降。最大化吞吐需要静态输入形状，因此编码器按其可能被调用的每一种形状分别编译。Cosmos 3 训练跨三种空间分辨率（$256\text{p}$、$480\text{p}$、$720\text{p}$）以及每种分辨率下的五种宽高比。在每个（分辨率，宽高比）组合内部，因果 tokenizer 以两种模式被调用：prime 块编码，以及缓存大小为 $1$ 和 $2$ 的分块编码。这产生 $3\times 5\times 3=45$ 张不同的计算图，必须在训练开始前全部编译完成。在每个 rank 上串行编译全部 $45$ 张图会使训练器启动时间增加约 $15$ 分钟。

为消除这一开销，我们使用 AOTInductor（PyTorch Contributors, 2026a）把编译跨数据并行 rank 分片，如图 15 所示；AOTInductor 执行提前编译（ahead-of-time compilation），并把所得内核与宿主代码序列化到磁盘。只要有至少 $45$ 个 rank（我们所有的训练配置都满足这一点），每个 rank 恰好编译一张图；编译产物写入共享文件系统，随后每个 rank 从磁盘加载完整的 $45$ 张图。这把预热开销降到一分钟以内。为在静态形状编译下容纳帧数任意的视频，每个输入片段在编码前先右填充到所配置的编码块大小的下一个整数倍，所得隐变量张量在被模型消费之前沿时间轴裁剪到精确的预期序列长度。

#### 特化到已知帧数。

对于每片段帧数固定且可先验得知的数据集——例如机器人动作数据集，其中每条 episode 都贡献等长的片段——我们把编译特化到运行时实际出现的精确张量形状，绕过一般情形下使用的“填充与裁剪”回退路径。这消除了填充尾部的计算，移除了相应的隐变量裁剪步骤，并在此类数据集上带来小幅但稳定的额外吞吐提升。

### 5.2.7 Checkpoint 保存

为消除保存导致的停滞，checkpoint 保存与训练完全重叠。沿用 Torchtitan（Liang et al., 2024b）的做法，checkpoint 写入经由一个专用的 Gloo 进程组路由，而不是承载训练集合通信的 NCCL 通信器，从而把 I/O 流量与 GPU 侧通信隔离开。这一异步设计隐藏了对象存储高度波动的写入延迟，并几乎消除了全部保存期开销，代价是主机内存的适度增加。Tab. 7 量化了所得收益：相对于 30 分钟间隔的同步 checkpoint，异步 checkpoint（asynchronous checkpointing）使 Cosmos3-Nano 的端到端训练时间减少 $4\%$，Cosmos3-Super 减少 $9\%$。

#### 异步保存机制。

在构造时，checkpointer 使用 spawn 启动方法派生一个长生命周期的子进程，并通过 multiprocessing 队列与之通信。该子进程加入一个 Gloo 进程组，并执行构建保存计划所需的 CPU 侧归约，从而把 GPU 留给训练使用。随后它阻塞在入站队列上，直到收到一次 checkpoint 保存请求或一个终止哨兵（sentinel）。

#### 保存计划记忆化。

为进一步降低开销，checkpoint 保存计划在第一次 checkpoint 保存操作期间计算，并在后续保存中复用。这之所以可行，是因为保存计划是 state-dict 拓扑的确定性函数。复用该计划避免了跨 rank 重复的元数据通信，并把 checkpoint 开销降低约 **60%**，进一步减少了异步 checkpoint 成为训练瓶颈的可能性。

#### 针对对象存储的优化。

在 checkpoint 保存期间，每个 rank 把其状态字典的本地分片写入对象存储。可能存在于多个 rank 上的复制张量在写入之前会被去重。在默认的轮询（round-robin）分配下，复制张量可能由不同 rank 写入，这要求每个 rank 在加载期间读取全部 checkpoint 文件才能恢复复制的状态。这会引入显著开销，因为即使只需要文件中的一部分内容，也必须加载整个文件。为降低这一开销，我们设置 dedup_to_lowest_rank = True，它把复制张量仅存储在相应 submesh 中编号最小的 rank 上，通常是 rank 0。于是在加载时，每个 rank 只需读取它自己的分片以及 rank-0 分片。这显著缩短了 checkpoint 加载时间，对包含大量小型复制张量的优化器状态字典尤为明显。

#### 随机状态恢复。

训练器以 rank 感知的方式恢复随机数生成器（RNG）状态。由于 RNG 状态以 rank 为键，恢复的作业首先检查 checkpoint 元数据中对应于自身 rank 的键，仅在其存在时才请求该状态。这保持了对早于 rank-键 RNG 格式的旧 checkpoint 的兼容性。若该 rank 专属键不存在，则该 rank 保留其当前的 RNG 状态。

## 5.3 服务基础设施

Cosmos 3 与多个生产级服务框架集成，以支撑广泛的部署场景。Reasoner 由 TensorRT-LLM（NVIDIA Corporation, 2026）与 vLLM（Kwon et al., 2023）支持，二者都通过分页 KV-cache 管理、连续批处理（continuous batching）与融合的注意力内核，提供高度优化的自回归解码。Generator 推理由 vLLM-Omni（vLLM 面向扩散式生成的多模态扩展）（Yin et al., 2026）支持，它在峰值吞吐与多租户调度效率之间提供互补的权衡。除这些生产后端之外，我们还提供原生 PyTorch 的参考实现，优先保证可读性与可修改性：它既是推理算法的忠实规范，也是下游适配、研究性扩展以及接入定制应用流水线的起点。

### 5.3.1 原生 PyTorch

原生 PyTorch 服务路径在 eager 模式的 PyTorch 中直接执行模型及其外围的推理流程——不依赖专门的服务运行时——其设计尽可能忠实地镜像训练期的计算。该路径负责完整的端到端推理工作流，包含下述阶段：

- • *输入准备。* 解析文本提示词，加载任何图像、视频或动作条件，构造模型所消费的模态专属条件字典，并组装相应的输入张量与元数据。

- • *自回归循环。* 在 Cosmos 3 Reasoner 中，输出 token 以自回归方式产生，每一步以先前生成的 token 以及条件上下文的已缓存 key/value 状态为条件。

- • *扩散循环。* 在 Cosmos 3 Generator 中，PyTorch 路径构建时间步调度，在每一步调用去噪器，施加无分类器引导（classifier-free guidance, CFG），按采样器更新隐变量状态，并管理去噪过程外围的请求级控制流。

- • *解码与后处理。* 去噪完成后，所得隐变量表示被解码到目标模态——文本、图像、视频、音频或动作——按需做后处理，并通过服务接口返回给调用方。

由于原生 PyTorch 后端保留了模型原始的 PyTorch 结构，它是落地新模型特性、采样器修改、KV-cache 与激活缓存策略以及调试仪表的首要目标。新能力先在此后端验证，随后才移植到生产运行时（TensorRT-LLM 与 vLLM），从而确保参考实现始终是推理算法的权威规范。PyTorch 后端暴露以下特性与优化。

#### 带 CUDA graphs 的 torch compile。

由于 PyTorch 原生推理路径把请求编排与采样逻辑留在 Python 中，服务的一个主要瓶颈是反复去噪步中的宿主侧内核启动开销。因此我们用 torch.compile 与 CUDA graph 重放来优化 PyTorch 路径。CUDA graph 优化以 Transformer 层为粒度实现，捕获重复执行的 Transformer 块。每个块以 reduce-overhead 模式用 torch.compile 编译，使 PyTorch Inductor 能够降级该块，并在该块以兼容的张量形状与内存布局被调用时改用 CUDA graph 重放。外层推理循环保持普通 PyTorch，即提示词处理、时间步调度、采样器更新、CFG 编排、解码都不进入被捕获的图。图中包含计算量大且高频重复的逐层计算，而动态的服务逻辑留在图外。CUDA graphs 的收益在 T2I 类生成上最为可见——较短的生成负载与较小的内核使 CPU 启动开销占据端到端延迟的更大比例。CUDA Graphs 为 T2I 生成在不同硬件后端上带来 30% 到 60% 的加速。

#### 分布式推理。

我们在推理时使用上下文并行（CP），以支撑超出单 GPU 显存容量约束的生成。我们保留训练期使用的 Ulysses 方案（Jacobs et al., 2023），确保两种情形之间的一致性。除支持长上下文推理之外，CP 还通过把前向传播分散到多块 GPU 上而充当一种降低延迟的机制；即便在单设备显存足以容纳完整上下文的场景下，这一收益依然成立，使 CP 成为加速推理的通用工具。

除上下文并行之外，我们还利用无分类器引导（CFG）并行进一步降低端到端推理延迟。带 CFG 的扩散采样在每个去噪步需要两次模型前向——一次以输入提示词为条件，一次无条件——两者的噪声预测被线性组合以产生引导后的更新。由于条件与非条件两次前向作用于相互独立的输入，且每个步只需同步一次以形成引导预测，它们是跨两块 GPU 并行化的理想对象。实践中我们并发地派发条件批次与非条件批次，并只做一次轻量的点对点交换来合并两个预测，然后推进采样器。这几乎把单步延迟减半，并与上下文并行干净地组合，在多 GPU 节点上带来乘性倍的延迟缩减。

#### Reasoner 塔缓存。

对于文本到图像（T2I）、文本到视频（T2V）、图像到视频（I2V）与视频到视频（V2V）生成等任务，Reasoner 塔的条件输入——文本提示词，以及适用时的条件图像或视频——在整条采样轨迹期间固定不变。因此 Reasoner 的输出在各扩散步之间是不变的，只依赖于条件，而不依赖当前噪声水平或部分去噪的样本。我们利用这一性质：在推理开始时计算一次 Reasoner 前向传播，并缓存其输出以供后续所有去噪步复用。由于被缓存的激活与在每一步重新计算所得结果在数学上完全相同，该优化在完全不影响生成质量的前提下显著降低了单步延迟。

#### 批处理。

把多个样本批量并入单次前向可以进一步提升推理吞吐，从而把每步开销（内核启动、权重读取与集合通信）摊到更大规模的有效工作上。我们的推理批处理器复用为训练开发的变长序列打包机制：它不是把较短序列 padding 到统一长度（那会把计算与显存都浪费在 padding token 上），而是把异构形状的样本拼接成单一打包张量，并向注意力及其他形状敏感算子提供相应的累积序列长度元数据。用户指定两种预算模式之一：总 token 预算（一个批次内允许的最大 token 数）或固定样本数。给定所选预算，批处理器贪婪地打包进入的样本直到预算耗尽，同时遵守任何单设备显存约束。这一设计提升了吞吐导向部署（例如离线语料生成与大规模评估）中的 GPU 利用率，但在延迟受限的设置（例如机器人工作负载）中没有收益——那里单个样本必须独立处理；在这些情形下，批处理器被配置为样本数一，实际上处于禁用状态。

#### 配合提示词上采样的生成。

推理另外支持一种提示词上采样（prompt upsampling）模式（更多细节见第 6.3.2 节），其中简短、自由形式的用户提示词由 Reasoner 扩展为对期望输出更丰富、结构化的 JSON 描述（涵盖例如场景构成、主体属性、相机与运动规格、光照与风格）。上采样后的描述由 Reasoner 自回归生成，随后作为附加条件输入送入 Generator，与用户提供的任何图像、视频或动作条件一起合成最终输出。这一流水线有两个用途：它把细致提示词工程的负担从终端用户转移给模型本身，稳定地改善下游生成质量；并在单次推理调用中贯通检验了 Reasoner 与 Generator 两条通路上的完整全模态端到端流程——证明两条通路可以被无缝组合，从最简的用户规格产出高保真的多模态输出。

#### 吞吐与服务考量。

推理工作负载一般优化两个相互竞争目标之一：吞吐或延迟。批量推理——为一组固定的输入语料生成大批输出——通常以吞吐为优化目标，因为受关注的指标是端到端墙钟时间与总成本。相反，延迟敏感的应用——例如机器人，动作必须从特定的起始上下文产生且有严格的每步截止时间——优先考虑响应速度，其相关指标是首 token 时间（或首动作时间）与单步延迟。上文所述的各项优化对这些情形的侧重各不相同：分布式推理（上下文并行与 CFG 并行）主要通过把单个请求跨多设备并行化来降低延迟，而批处理主要通过跨多个并发请求摊薄每步开销来提升吞吐。其余优化——torch compile 与 reasoner 输出缓存——则同时惠及两种情形。

### 5.3.2 Reasoner 的推理框架：vLLM 与 TensorRT-LLM

由于 Nano 与 Super Reasoner 构建在 Qwen3-VL（Bai et al., 2025b）骨干之上，它们接入 vLLM 与 TensorRT-LLM 时复用了两个框架中已有的上游 Qwen3-VL 支持。这让我们能够开箱即用地继承两个后端本已为 Qwen3-VL 家族提供的优化注意力内核、分页 KV-cache 管理、连续批处理与多模态输入处理，只需极少的配置改动即可把 Cosmos 3 的模型权重与 tokenizer 绑定到既有的执行路径。

相比之下，Edge Reasoner 构建在自定义的 Nemotron 骨干（NVIDIA, 2025f）之上，vLLM 并不原生支持它。因此我们遵循 vLLM 模型贡献者的规范实现了一个专门的集成。该集成在结构上便于向上游游说合入（upstreamable），从而降低未来的维护成本并方便社区贡献。

### 5.3.3 Generator 的推理框架：vLLM-Omni

Cosmos 3 Generator 被集成进 vLLM-Omni，以利用其为扩散式多模态生成优化的服务栈。该集成把 Cosmos 3 Generator 实现为一等公民的 vLLM-Omni 模型，并支持完整的 Generator 模态集合，包括图像、视频、音频与以动作为条件的生成。它遵循 vLLM-Omni 框架的模型贡献者规范与代码风格，使实现与框架既有的调度、分布式执行、显存削减与量化特性相兼容。

这一集成对 Generator 服务尤为重要，因为扩散式生成需要对大规模的图像、视频或多模态 token 序列进行大量重复的 Transformer 求值。vLLM-Omni 后端因而聚焦于降低单步延迟、削减峰值显存占用并提升吞吐，同时保持生成质量。Cosmos 3 Generator 的集成支持以下 vLLM-Omni 特性：

- • *Cache-DiT。* 一种免训练的加速方法，在相邻去噪步之间复用被缓存的 Transformer 块输出，从而跳过冗余计算，对生成质量的影响可忽略。

- • *Ulysses 上下文并行。* 一种上下文并行的执行方案，把长的图像与视频 token 序列分片至多块 GPU，并使用 all-to-all 注意力通信来降低单设备显存占用并改善延迟。

- • *CFG-Parallel。* 一种针对无分类器引导的并行化策略，把条件与非条件前向传播分发到不同的 GPU rank。两个预测在每个去噪步同步一次以形成引导更新，从而降低基于 CFG 的采样延迟。

- • *HSDP。* 一种显存高效的分布式推理模式，使用 FSDP2 把 Transformer 权重分片到多块 GPU，并在前向传播期间按需聚集参数，降低大型 Generator 模型的峰值显存需求。

- • *CPU offload。* 一种逐层卸载机制，在推理期间于 CPU 与 GPU 显存之间搬运模型参数，用额外的数据传输开销换取大幅降低的峰值 GPU 显存占用。

- • *VAE-Patch-Parallel。* 一种并行 VAE 执行模式，把隐变量或像素张量按空间图块切分，并在多个 rank 上对其编码或解码，同时降低单设备显存消耗与 VAE 延迟。

- • *量化。* 一条动态 FP8 量化路径，降低主要计算操作的精度以减少推理延迟与峰值 GPU 显存占用，同时保持可接受的生成质量。

这些特性共同使 Cosmos 3 Generator 能够从显存受限的单 GPU 部署扩展到高吞吐的多 GPU 服务。Cache-DiT 与量化降低重复去噪计算的成本；上下文并行与 CFG-Parallel 通过跨 GPU 分发单个请求改善延迟；HSDP、CPU offload 与 VAE-Patch-Parallel 则为高分辨率或长时长生成任务减轻显存压力。图 16 汇总了 Cosmos3 的服务性能：既比较不同硬件后端上的单 GPU 运行，也比较 B200 上的多 GPU 运行。评估在 PyTorch-OSS 与 vLLM-Omni 两个框架下进行。

## 5.4 基准测试基础设施

Cosmos 基准系统管理 Cosmos 模型的评估作业，并同时存储生成的产物与评估结果。一个编排层在 Lepton 或 Slurm 集群上调度生成、打分与端点评估作业，并跟踪每个阶段的执行状态。对每一次运行，系统记录元数据，包括模型 checkpoint、代码版本、所选基准、生成设置、基准专属参数以及相关数据集。这些记录共同建立了每个上报分数与产出该分数所使用的精确模型权重、输入、参数配置及评估代码之间的完整可追溯性。

该系统支持第 6 节所描述的异构基准套件，而不要求所有基准共享同一实现。基准评估生成视频、音频、动作轨迹以及 reasoner 模型的文本回答，覆盖一组多样的准则，包括视觉保真度、音频质量、音画同步、提示词与控制遵循度、动作或轨迹精度、任务完成度、物理合理性与推理正确性。评估器既包括与开源库及公开基准套件的集成，也包括为 Cosmos 专门开发的自定义评估器。打分方法涵盖基于参考的误差指标、感知与时间一致性度量、音视频对齐指标、基于 VLM 的评审（judge）、人工标注，以及精确匹配或数值答案评估。

对于 Generator 评估，基准测试被分为生成与打分两个阶段。生成作业使用 PyTorch 推理流水线，或第 5.3 节所述的某个服务框架来执行模型，并把生成输出写入对象存储。打分作业随后消费这些已存储的产物，计算逐样本与聚合指标，并把结果连同运行元数据一并记录。这一解耦设计允许用新的指标或评估器对输出重新打分，而无须重跑生成。

对于 Reasoner 评估，我们使用 VLMEvalKit（Duan et al., 2024）框架配合 vLLM。这些作业向已部署的模型端点发送提示词与多模态输入，处理模型响应，并记录基准分数与相关元数据。

评估分数与运行元数据存储在关系型数据库中，生成的产物存储在对象存储中。人工评估标注与被评估的产物及问题集一并存储，聚合后的人工评估结果与自动化指标并行跟踪。一个基准门户通过仪表盘、排行榜、样例级检查工具以及模型对模型、checkpoint 对 checkpoint 的比较，向这些记录提供访问。
