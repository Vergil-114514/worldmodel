## 4. 训练（Training）

我们以两个主要阶段训练 Cosmos 3。第一，Reasoner（推理器）在大规模图文与视频-文本语料上进行预训练，随后在精选的 Physical AI（物理 AI）数据混合上进行微调，从而产出用于视觉理解与推理的强大多模态骨干网络。由于 Reasoner 与 Generator（生成器）共享同一套 Transformer 模块（block）架构，训练好的 Reasoner 权重随后被用来初始化 Generator，将语义与世界知识迁移进一个能够合成像素、音频与动作的模型。Generator 采用渐进式多阶段课程（curriculum）进行训练：首先进行大规模图像、视频与音频预训练，随后是通过中期训练（mid-training）逐步引入动作与 transfer（迁移）数据，最后在规模更小、经精心筛选的 Physical AI 数据集上进行后训练（post-train），以改善下游行为、物理一致性与动作保真度。

### 4.1 推理器训练（Reasoner Training）

Cosmos 3 Reasoner 分两个阶段训练：先进行大规模多模态预训练，然后在精选的 Physical AI 任务上进行监督微调（supervised fine-tuning）。在预训练期间，模型从大规模图文与视频-文本语料中学习通用多模态表征。监督微调随后将模型专门化到 Physical AI 领域，包括机器人、自动驾驶与智能基础设施应用，同时保留预训练阶段获得的广泛能力。

#### 4.1.1 预训练（Pre-Training）

Reasoner 预训练从一个语言模型和一个 ViT 编码器出发，二者通过一个多模态投影器（projector）连接。在初始化方面，我们同时尝试了附录 D 中描述的内部预训练模型与开源的 Qwen3-VL 模型：Edge 模型使用我们内部预训练的模型，Nano 模型使用 Qwen3-VL-8B，Super 模型使用 Qwen3-VL-32B。与此前只训练投影器、冻结其余 VLM 参数以进行单独对齐阶段的做法（Bai et al., 2025a）不同，我们发现这种分阶段对齐并无必要，而是从预训练一开始就联合训练所有组件。

模型使用下一 token 预测（next-token prediction）目标，在第 3.1.1 节描述的大规模多模态语料上训练。我们在完整预训练混合数据上训练两个 epoch，采样器采用不放回（no-replacement）方式，均匀拼接所有数据集。由于许多 Physical AI 应用要求高效推理与低延迟推理，我们将训练限制在最长 16k token 的序列上，其中每样本的图像 token 上限为 2048，视频 token 上限为 8192。

沿用先前工作（Bai et al., 2025a; Wang et al., 2025e），我们对逐 token 损失施加平方根归一化加权，以平衡短序列与长序列的贡献。我们发现这一归一化策略显著提升了下游基准分数与整体训练稳定性。

优化使用 AdamW：语言模型与投影器的峰值学习率为 5×10⁻⁵，ViT 为 5×10⁻⁶。所有学习率均按余弦衰减（cosine decay）调度，先经过 10% 的线性 warm-up 阶段，再衰减至峰值的 0.1×。Adam 系数 (β₁, β₂) = (0.9, 0.999)。训练另外使用权重衰减（weight decay）0.05，以及全局范数阈值为 1.0 的梯度裁剪。

#### 4.1.2 监督微调（Supervised Fine-Tuning）

为使模型适配下游 Physical AI 任务，我们在精选的高质量多模态混合数据上进行监督微调。与预训练中各数据集跨 epoch 均匀采样不同，监督微调采用一种重要性感知（importance-aware）的采样策略：为每个数据集依据其重要性、质量与规模分配固定的采样预算。这使得优化能够聚焦于高价值的下游任务，同时保持跨领域、跨能力的多样性。

为防止下游专门化损害模型的通用推理与视觉理解能力，我们还额外混入经过滤的高质量预训练数据子集，预训练与 SFT 的采样预算之比固定为 1:4。保留少量预训练数据流可提升鲁棒性、保持指令遵循行为，并在多个基准上维持强大的通用领域能力。我们还在监督微调混合数据中加入一个轻量级指令遵循数据集（800K 样本），以在任务适配期间进一步稳定对话与指令遵循能力。

训练共进行 8200 次迭代，全局批大小（global batch size）为 512。我们使用 AdamW 优化器：语言模型与投影器的峰值学习率为 1×10⁻⁵，ViT 为 1×10⁻⁶。所有学习率均按余弦衰减调度，在 1000 步线性 warm-up 之后衰减至峰值的 0.1×。Adam 系数 (β₁, β₂) = (0.9, 0.95)。权重衰减为 0.1，梯度裁剪的全局范数阈值为 1.0。

### 4.2 生成器训练（Generator Training）

Cosmos 3 Generator 采用渐进式多模态课程训练，旨在跨不同分辨率、时长与条件模态，联合建模视觉、听觉与动作条件下的世界动态。该训练配方强调可扩展性、高保真生成与高效长上下文学习。在预训练阶段，模型从涵盖图像、视频与音频的大规模数据中学习一般性生成先验。其后的训练阶段逐步引入更丰富的多模态监督，包括动作与 transfer 序列，使模型学习到时间上连贯的世界演化与物理基础扎实的交互。

**训练目标。** Cosmos 3 Generator 在所有模态上以 rectified flow matching（校正流匹配）目标进行优化。对来自任意模态的目标隐变量（latent），我们通过直线插值构造带噪隐变量：

$$x_\tau = \tau \cdot x_1 + (1-\tau) \cdot x_0$$

其中 $x_0$ 为干净目标，⟨原文公式符号在文本抽取中丢失，待对照 PDF 复核：$x_1$ 的分布，按上下文应为 $x_1 \sim \mathcal{N}(0, I)$⟩，$\tau \in [0, 1]$ 为噪声水平。单个去噪器 $f_\theta(x_\tau, \tau, c)$ 通过带掩码的均方误差（masked MSE）训练以预测恒定速度

$$v^* = \langle\text{原文公式符号在文本抽取中丢失，待对照 PDF 复核：按上下文应为 } x_1 - x_0\rangle$$

其中条件 token（例如 image-to-video 任务中的干净条件帧）通过门控从损失中剔除。我们对各模态独立地进行时间采样：噪声水平 $\tau$ 对每个模态（图像、视频、音频与动作）独立抽取。遵循 Waver（Zhang et al., 2025c），图像、音频与动作批次使用 logit-normal 噪声分布，视频批次使用 mode sampling（模式采样）。我们发现使用 mode sampling 能带来更好的生成质量。我们进一步通过 rectified-flow shift 重参数化映射 $\tau$：

$$\tau' = \langle\text{原文公式符号在文本抽取中丢失，待对照 PDF 复核：按上下文应为 } \sigma \cdot \tau / (1 + (\sigma - 1)\cdot \tau)\rangle$$

其中 ⟨原文此处符号在文本抽取中丢失，待对照 PDF 复核（此处出现 “= 1 - ” 片段，含义无法确证）⟩，$\sigma$ 越大，边际分布越偏向更高的噪声水平。

#### 4.2.1 预训练（Pre-Training）

在预训练阶段，我们联合训练模型，以跨不同分辨率与生成任务生成图像、视频与音频。为支撑这一点，我们采用多分辨率训练策略，并在多个生成任务上联合优化模型，包括 Text-to-Image（文生图）、Text-to-(Video+Audio)（文生视频+音频）、Image-to-(Video+Audio)（图生视频+音频）与 Video-to-(Video+Audio)（视频生视频+音频）。

**多分辨率训练。** 我们不锁定单一输出分辨率，而是同时在三个分辨率档位（256p、480p、720p）、五种宽高比以及可变帧数上进行训练，如 Tab. 5 所示。这使模型得以接触高保真内容，同时促使表征与分辨率无关。训练数据相应地划分：256p 数据流使用全部数据集（任何原生分辨率均可入选），480p 数据流仅限原生分辨率不低于 480p 的源素材，720p 数据流只使用不低于 720p 的内容，从而在最高档位保留锐度与细节。每个分辨率档位施加不同的最大帧数预算：256p 与 480p 至多 400 帧，720p 为 300 帧。720p 限制为 300 帧是出于序列长度约束。训练批次在四个档位（image-only、video-256p、video-480p、video-720p）之间按 1:1:2:1 的比例组合。我们发现这一分布在高保真学习与样本多样性之间提供了很好的平衡：模型既能观察到更多训练样本，又强调更高分辨率的内容。我们使用分辨率自适应的 shift 值：256p 时 σ = 1，480p 时 σ = 3，720p 时 σ = 5。

为避免无谓的重复编译开销同时支持可变序列长度，我们采用 token 打包（packing），每条序列固定预算为 74,000 个 token。不同分辨率的序列被打包在一起填满每个批次，在不使用 padding 的情况下最大化 GPU 利用率（见 Fig. 10 的描绘）。

**训练模式。** 对于形状为 ⟨原文符号在文本抽取中丢失，待对照 PDF 复核：按上下文应为 T×H×W×C⟩ 的隐变量视频张量，记 cond 为条件隐变量帧数，noised 为带噪隐变量帧数（⟨符号丢失，按上下文应为 T = cond + noised⟩）。训练时，前 cond 帧不施加任何噪声，作为条件输入；仅对其后 noised 帧加噪，并让模型学习去噪。cond 与 noised 的不同取值产生不同的训练模式。我们使用四种生成模式——Text-to-Image、Text-to-Video、Image-to-Video 与 Video-to-Video——它们仅以每个样本前置的条件视觉帧数区分，采样比例分别为 20%、56%、16% 与 8%。所有模式都使用第 3.2 节描述的结构化 JSON caption 格式。

- **Text-to-Image（T2I，文生图）。** 图像被视为时间维限制为 ⟨符号丢失，按上下文应为 T = 1⟩ 的视频特例。在该模式下，图像从全部三个分辨率档位与各种宽高比中随机抽取，随后进行序列打包再送入模型。由于单个图像样本产生的 token 远少于视频，一条典型序列包含的图像样本数远多于视频序列。
- **Text-to-Video（T2V，文生视频）。** 在文生视频训练中，cond = 0。模型学习仅以文本为条件对整段视频去噪。除 caption 外，模型还接收时长、FPS 与时间戳元数据作为 JSON caption 中的附加字段，使其能够生成指定长度与时间跨度的视频。
- **Image-to-Video（I2V，图生视频）。** 对于单帧条件（cond = 1），第一个隐变量帧保持干净，其后各帧加噪。模型学习生成与初始帧及 caption 都一致的未来帧。
- **Video-to-Video（V2V，视频生视频）。** 对于多帧条件（cond = 2），模型以视频的前五帧（等价于前两个隐变量帧）为条件，学习生成与条件帧及输入提示词都一致的未来帧。

**FPS 调制。** 我们以不同的 FPS 值训练模型，因此 token 之间的物理时间间隔在不同样本间存在差异：以 30 FPS 采样的片段在真实时间上比同样 token 数以 16 FPS 采样的片段帧间更密。为反映这一点，我们调制 3D MRoPE 位置编码的时间轴——按真实世界时间而非 token 索引成比例地赋予时间坐标（见第 2 节），基准速率为 24 FPS。时长与 FPS 也被追加到文本提示词中，使模型在推理时能够以特定的时间特性为条件。

**优化。** 生成器预训练期间只更新生成专用参数。Reasoner 塔保持冻结，以保留语言与视觉理解能力。我们使用 FusedAdamW，学习率 10⁻⁴，(β₁, β₂) = (0.9, 0.99)，权重衰减 0.05，梯度裁剪范数 1.0。学习率调度采用带 warm-up 的线性衰减，从峰值学习率降至 ⟨符号丢失，按上下文应为峰值的 0.30×⟩ 的下限，衰减过程贯穿 ⟨抽取文本此处缺词，按上下文应为全部训练迭代⟩。为支持 classifier-free guidance（无分类器引导，CFG），文本 dropout 率在全部模态上设为 10%。

**训练 token 数。** 在预训练阶段，Cosmos3-Nano 在 1024 块 NVIDIA GB200 GPU 上训练了 31.05T 个 token；Cosmos3-Super 在 2048 块 NVIDIA GB200 GPU 上训练了 17.86T 个 token。

#### 4.2.2 中期训练（Mid-Training）

中期训练弥合了大规模预训练与下游部署之间的鸿沟。此时 Generator 已从大规模数据中学到一般的图像、视频与音频生成，但目标 Physical AI 应用要求对罕见动态、具身场景、控制接口与高质量视觉领域有更强的覆盖。因此我们从预训练 checkpoint 继续训练，使用一个精心构建的混合数据集，既保留原有视觉生成模式，又引入新的监督来源。该阶段有两个互补的目标：领域专门化（domain specialization），即增加对高价值 Physical AI 领域的暴露；多模态整合（multimodal integration），即把模型从视觉与音频生成扩展到以动作和控制为条件的世界建模。

**领域专门化。** 在保留通用知识的同时，让模型接触高度精选的专门数据集，以提升应用关键型 Physical AI 场景中的质量与可靠性。对图像，我们使用一个 15.6M 样本的中期训练池，侧重高质量真实图像，同时加入合成与文字渲染数据以拓宽概念覆盖并保持可读的文字生成。对视频，我们纳入 74.7M 经筛选的片段，涵盖机器人、自动驾驶、人类活动、物理与合成仿真数据。这些来源针对的是通用网络级预训练中代表性不足的失效模式，例如长时程交互、细粒度的人与机器人运动、物体物理动态，以及安全关键的驾驶或仓储场景。通过把这些领域聚焦的数据集与既有图像、视频训练模式混合，中期训练在不丢弃预训练所学宽泛视觉先验的前提下提升 Physical AI 相关性，如第 3.2.1 节所述。

**多模态整合。** 中期训练把 Generator 从图像、视频与音频生成扩展为一个统一的 Physical AI 模型，使其能够消费并合成动作与控制信号。我们沿用预训练中 T2I、T2V、I2V、V2V 所用的"干净前缀/带噪目标"公式，因此现有视觉能力保持激活，同时新的模态专用 token 被引入扩散子序列中。这使得动作、音频、控制与视频 token 共享第 2 节描述的同一时间坐标系与双向注意力模式。除预训练模式之外，我们新增两大类多模态监督：动作（action）与视频迁移（video transfer）。

- **视频迁移（Video transfer）。** 我们加入以控制为条件的迁移数据：将干净的控制信号作为输入，模型对相应的目标图像或视频去噪。控制信号包括来自高质量视频语料的边缘（edge）、模糊（blur）、深度（depth）与分割（segmentation）图，以及用于驾驶场景的世界场景图（world-scenario maps）。这让模型接触到空间上落地的约束，同时保留文本条件与视觉生成质量。

各模态的混合比例见 Tab. 6。

**多分辨率训练。** 与预训练类似，中期训练在固定 74K 上下文窗口内跨 256p、480p 与 720p 进行多分辨率训练。为更好地处理动态并减少时间与高分辨率伪影，我们将 rectified-flow shift 值提高为：256p 用 3、480p 用 5、720p 用 10。

**训练目标。** 与预训练类似，所有模态均使用 rectified flow 目标。对动作，我们继承视觉的噪声调度。中期训练的总损失是各模态速度 MSE 之和，并按模态专属损失系数加权，其中动作损失乘以 10× 系数，以补偿归一化动作向量逐元素 MSE 较小的问题。

**优化。** 与预训练类似，我们使用 FusedAdamW，学习率 10⁻⁴，权重衰减 0.05，梯度裁剪范数 1.0，loss scale 为 10。学习率采用 LambdaLinear 调度，起始因子 0.4，循环长度 100,000。

**训练 token 数。** 在中期训练阶段，Cosmos3-Nano 在 1024 块 NVIDIA GB200 GPU 上训练了 2.4T 个 token；Cosmos3-Super 在 2048 块 NVIDIA GB200 GPU 上训练了 1.9T 个 token。

#### 4.2.3 文生图后训练（Text-to-Image Post-Training）

为展示 Cosmos3-Super 的全模态（omnimodal）能力，我们进一步将模型专门化为文生图 checkpoint——Cosmos3-Super-Text2Image。我们的目标是将模型具有物理基础的世界理解迁移到高质量图像生成，力争取得强开源 T2I 结果，同时提升物理合理性与场景级对齐。

我们采用两阶段 SFT 进行文生图专门化，遵循通用的文生图基础模型训练范式：先强调语义增强，再进行偏好导向的精炼。

- **阶段 1：广泛 T2I 专门化（broad T2I specialization）。** 我们在精选的高质量 SFT 数据集上微调模型 20k 训练步。训练混合按受控比例采样：45% 通用真实图像数据、40% 合成图像数据、15% 仅文字渲染数据，以平衡视觉保真度、caption 对齐与语言保留。基础学习率为 1×10⁻⁴，warmup 2k 迭代，采用线性学习率衰减调度，其余所有超参数与 Cosmos 3 中期训练阶段保持一致。
- **阶段 2：高质量精炼。** 我们使用 470k 张精心筛选的超高质量图像-caption 对，进行最后一轮 2k 步的 SFT。该阶段进一步提升视觉美感、提示词遵循、文字渲染质量以及与人类偏好的对齐。
- **分辨率与上下文长度。** 两个阶段均使用 70k token 的固定上下文窗口，且只在分辨率高于 720p 的图像上训练。

总体而言，Cosmos3-Super-Text2Image 在语义对齐与英文文字渲染基准上都取得了强劲的文生图结果。在 UniGenBench 上，它在被评估模型中取得最佳总分，完整基准达到 91.36（见 Tab. 11）。配合 agentic 工作流，该模型在 Artificial Analysis Text-to-Image 排行榜（第 6.2.1 节）上位列开源权重模型第一。这些结果表明，从 Cosmos 3 出发进行下游 T2I 模态适配极其有效：它在提升场景级提示词对齐的同时，保留了模型的物理基础生成能力。

#### 4.2.4 图生视频后训练（Image-to-Video Post-Training）

图生视频能力对于全面视觉理解具有根本性的重要意义。它检验模型对物理规律、物体恒存性与复杂场景几何的理解，同时作为具身 AI 与机器人规划的关键预测机制——模拟合理未来帧可形成一个有效的世界模型（Wiedemer et al., 2025; Chen et al., 2025a）。尽管 Cosmos 3 的固有设计即可原生处理多种任务，我们仍利用 SFT 显式展示并专门化其在 I2V 领域的潜力。为展示这些能力，我们采用如下流程：

- **数据与训练混合。** 我们使用经过滤、并针对更均衡主题多样性进行精炼的预训练数据来微调模型，再通过一个 agentic 工作流加以增强：该工作流识别模型的薄弱点，并据此从预训练集中检索针对性样本。上述数据与 1,000 条高质量人工精选视频，以及一个约 20k 条覆盖多样主题的合成视频片段数据集（约占总 token 数的 6%）组合使用。虽然所有视频序列都仅以 I2V 公式训练，我们的训练混合还包含 20% 的 T2I 图像 token，以保持模型的语义对齐能力。
- **分辨率与时长。** 我们将模型的时间生成能力专门化到目标分辨率 480p 与目标时长 189 帧，约相当于 24fps 下 8 秒。这一配置在推理速度与时间上下文之间取得平衡，从而在有意义的时间跨度上实现快速且物理合理的视频生成。
- **训练日程。** I2V 后训练阶段运行 10k 次迭代，学习率为 1×10⁻⁵。模型在整个 SFT 过程中处理约 50B token。

通过后训练，Cosmos3-Super-Image2Video 在图生视频生成上达到领先质量。特别地，该模型在 Artificial Analysis Image-to-Video 排行榜（第 6.2.2 节）上位列开源权重模型第一。关于该模型的使用细节，请参见第 6.3.1 节。

#### 4.2.5 机器人策略后训练（Robot Policy Post-Training）

我们开展机器人策略后训练，以探究 Cosmos 3 全模态世界模型能否被扩展为强大的机器人策略模型。中期训练使 Cosmos 3 能够对多模态序列——包括语言、视觉观测与动作——建模，并联合生成动作与视频。我们进一步通过引入本体感知（proprioceptive）信号、降低推理延迟，并让模型适配生成可执行动作以进行闭环控制，从而将其定制用于机器人策略学习。

作为先导研究，我们选用 DROID 机器人平台与数据集（Khazatsky et al., 2024），原因在于其受欢迎程度与广泛的社区采用。DROID 平台使用一台 Franka Panda 7 自由度（7-DoF）机械臂，配备 Robotiq 2F-85 平行夹爪，在多样的真实环境中执行桌面操作任务。DROID 数据集包含 76k 条轨迹、350 小时交互数据、86 项任务与 564 个场景，为真实世界机器人策略学习提供了可观的规模与广泛的任务多样性。我们以 360×640 的高分辨率接入 DROID 数据，应用社区提供的空闲帧过滤与失败演示移除，并在训练中使用随机图像增强。

我们从中期训练得到的 Cosmos3-Nano 模型恢复训练，对 Cosmos3-Nano-Policy-DROID 进行后训练，并新初始化一个动作编码器、动作解码 MLP 与动作嵌入 token。我们对动作相关参数施加 5× 的学习率倍率以促进更快适配。策略输入由当前本体感知机器人状态与三视角视觉观测组成。具体地，腕部视角图像（原始分辨率 360×640）置于上方，其下并列两张外部视角图像（原始分辨率各为 180×320），分别拼接在左下与右下，形成 540×640 的画布。策略训练预测 32 个未来的绝对关节位置动作，并附带辅助 RGB 视频帧作为额外输出，运行频率为 15Hz。在该后训练研究中，我们使用官方 DROID 短任务指令作为提示词。学习率使用 2×10⁻⁴，其余超参数沿用中期训练设置。

推理时，我们以 4 个扩散步采样模型，噪声调度 shift 为 5。我们还施加 CFG 并行、引导尺度（guidance scale）为 3 的 classifier-free guidance，并跳过视频隐变量解码以进一步降低推理开销。这些优化综合带来显著的推理加速，使策略服务器可部署在 2 块 NVIDIA RTX Pro 6000 GPU 上。下游关节位置控制器基于 Franky（Schneider, 2023）实现，以 15Hz 执行预测出的 32 个动作。

总体而言，Cosmos3-Nano-Policy-DROID 在机器人策略任务上取得强劲结果。如第 6.2.5 节详述，在我们提交排行榜时点，它在 RoboLab（Yang et al., 2026a）、RoboArena（Atreya et al., 2025）与 MolmoSpaces（Kim et al., 2026）上均排名第一，证明了 Cosmos 3 作为机器人策略学习基础模型骨干的有效性。

## 5. 基础设施（Infrastructure）

本节描述为支撑 Cosmos 3 端到端生命周期而设计的一体化基础设施栈。如 Fig. 11 所示，平台统一了 4 大核心支柱：

- **数据工程（Data engineering）。** 接入原始多模态数据，并将其转换为 WebDataset 格式的精选数据集，针对可扩展的分布式训练进行优化。
- **大规模训练（Large-scale training）。** 通过高效并行化策略、优化的数据加载、快速 checkpoint 与集合通信原语，最大化 NVIDIA GPU 集群利用率。
- **模型服务（Model serving）。** 在生成式与推理式两类工作负载上实现高效、低延迟的部署与推理执行。
- **基准测试与验证（Benchmarking & validation）。** 提供统一评估框架，跨多样任务评估模型能力，支持自动化回归跟踪与系统化模型比较。

### 5.1 数据基础设施（Data Infrastructure）

Cosmos 3 训练语料取自数百亿（tens of billions）图像与视频候选，横跨多种模态、领域与任务。在这一规模上运转，要求数据基础设施同时具备三种能力：(1) 通过大规模分布式处理将原始多模态数据转化为可训练样本；(2) 支持基于嵌入的检索、聚类与去重；(3) 支持交互式的数据集可视化、检查与调试。为满足这些需求，我们开发了 SILA（Scalable Infrastructure for Large-scale data processing and Annotation，面向大规模数据处理与标注的可扩展基础设施），一个可扩展的多模态数据基础设施平台，将存储、元数据管理、分布式处理、语义检索与数据集可视化整合为单一可扩展框架，用于大规模数据整理与管理。

> **Figure 11:（图 11）** Cosmos 3 基础设施栈总览。平台横跨四大支柱。数据基础设施接入原始多模态数据流，并将其整理为 WebDataset 格式的训练分片。训练基础设施在 NVIDIA GPU 集群上以高效并行化、数据加载与 checkpoint 机制消费这些分片。所得 checkpoint 分为两条并行路径（以虚线分隔）：服务基础设施将其部署用于低延迟生成与推理；基准测试基础设施则用标准化基准数据集评估同样的 checkpoint，以跟踪回归并支持系统化验证。

SILA 围绕"流水线逻辑与基础设施机制的清晰分离"构建。研究者声明带类型的处理阶段——指定每个阶段消费的列与其产出的输出——而平台透明地处理数据集分片、分布式执行、容错、checkpoint、元数据更新与资产注册。这一抽象使得引入新的数据源、基础模型与处理阶段（包括过滤、caption 生成、嵌入生成、打分与打标）变得简单直白，无需研究者具备分布式系统专业知识。由此，平台让数据整理能以研究本身的节奏演进：随着模型、质量标准与训练配方的变化，新信号可以增量地被加入、重算或替换。

#### 5.1.1 大规模数据处理（Large-Scale Data Processing）

多模态数据整理是一个迭代式富集（enrichment）过程，而非一次性的离线预处理。随着模型、质量标准、标签与训练配方的演化，原始文本、图像与视频样本被反复变换、过滤、标注与再处理。扩展这一工作流很有挑战，因为该流水线既低产出又高度迭代：只有很小比例的原始候选最终存活进入训练，这意味着低效的扫描、拷贝或模型推理被不成比例地花在了后续会被丢弃的样本上。同时，接入（ingestion）、切分与转码、嵌入生成、去重、过滤、分类打标、caption 生成、分片等阶段要对同批样本反复操作。因此，支撑这一工作流需要对数十亿多模态样本进行重复变换与增量重算的高效机制。

这些挑战在分布式执行下更加突出。整理工作负载必须在共享集群上持续运行，而集群中的 GPU 可用性是碎片化且动态变化的，不能假设有单一整体式配额。基础设施必须协调大量分布式 worker、避免重复计算、从故障中恢复、管理 CPU 密集与 GPU 密集混合的阶段，并在资源出现时继续处理未完成的工作。为支持这一执行模型，SILA 结合了：统一数据层、fragment 级协调与故障恢复、分阶段分布式执行、节点内模型服务端点、机会主义集群利用，以及对 agent 友好的运维接口。

**统一数据层。** SILA 将数据整理组织为一个统一的列式 Lance 数据集（Pace et al., 2025）：每一行代表一个数据样本，每一个带类型的列代表一个整理信号，如 caption、标签、质量分数或标注。这取代了早期基础设施 Cosmos-Predict 1.0（NVIDIA, 2025d）与 2.5（NVIDIA, 2025b）所采用的"每流水线一张表"架构——彼时每条流水线写入自己的 Postgres 表，输出之后通过 Change Data Capture（CDC）同步进 Databricks。随着流水线与元数据字段数量增长，"每流水线一张表"的设计需要跨大表越来越复杂的 join 才能重建单个样本的状态。这些 join 在大规模下代价高昂，即使简单的运维查询，若不详细了解 join 键、表关系与流水线专属模式也难以表达。相比之下，SILA 通过在共享 Lance 表上追加新的带类型列，对同一逻辑样本进行增量富集。这一统一表示天然契合多模态整理工作负载——多数阶段是对既有样本追加元数据，而非创建新实体。通过将数据集内容、元数据与处理状态共置一处，系统能够高效支持大规模扫描、点查、增量重算，并直接从 Lance fragment 元数据发现未完成的工作，而无须昂贵的启动期 join。

**Fragment 级协调与故障恢复。** 这一规模下的整理以高并发运行：单个作业内的许多分布式 worker 以及许多并行独立作业，都在对同一份持续演化的 Lance 数据集读写。若没有显式协调，worker 只能依赖昂贵的启动查询、随机采样或事后过滤已处理样本来避免重叠。这些做法延迟作业启动、允许重复计算，并使长时间运行作业被抢占或中断后的恢复复杂化。SILA 改为直接在 Lance fragment 层面协调分布式整理。worker 从 Lance 元数据中发现未完成的 fragment，并在处理前获取有时限的租约（lease），而 Lance 数据集本身仍是完成状态的唯一事实来源。租约所有权通过周期性心跳维持；心跳停止时租约到期，另一个 worker 可重新获取该 fragment，从而对故障、抢占或端点崩溃实现自动恢复，无须人工清理。由于单个 fragment 可能包含许多样本并需要数小时的模型推理，SILA 进一步把已认领的 fragment 划分为更小的处理段（segment），将完成的段作为持久 checkpoint 写出，待全部段完成后，通过一次元数据更新将整个 fragment 原子地提交回 Lance。这把恢复单元与可见性单元解耦：中断的作业从已完成的段继续，而下游读取者只看到完全提交的 fragment 输出。

**分阶段 Ray 执行。** 整理流水线混合了资源画像差异极大的异构操作，包括数据加载、解码、模型推理、后处理、写出与提交。若这些操作通过单一无差别的控制循环执行，快速的上游阶段会堆积中间输出，而较慢的推理或提交阶段会成为瓶颈。SILA 改为通过分阶段的 Ray 流水线引擎（Moritz et al., 2018）执行每个已认领的 fragment。框架管理的阶段负责加载、写出与提交；用户定义的 preprocess、compute 与 postprocess 阶段则在各司其职的 Ray actor 池中执行，各自独立配置 worker 数量与资源需求。背压（backpressure）限制跨阶段边界的在制品数量，防止快速的 I/O 密集阶段压垮较慢的下游阶段，并迫使 Ray 对象存储溢出到磁盘。

**节点内模型端点。** 基础模型整理工作负载往往需要在许多流水线 worker 并发处理数据的同时，服务大规模 caption、嵌入、打标或打分模型。集中式推理服务在大规模下可能成为瓶颈，而要求一大块连续 GPU 配额又会削弱利用集群碎片化可用资源的能力。SILA 转而使用 vLLM（Kwon et al., 2023）等系统启动节点内的模型服务端点，并把本地端点信息直接传给各阶段 worker。worker 随即调用节点内服务进行推理，使模型密集的整理阶段能跨可用节点扩展，并将数据并行的流水线执行与模型服务部署位置解耦。

**机会主义集群利用。** 大规模整理必须与训练工作负载在共享集群上并行持续运行，而集群 GPU 可用往往碎片化且动态变化。SILA 不要求单一整体式配额，而是把整理分解为细粒度分布式作业，可随资源出现而增量执行。系统支持 DGX Cloud Lepton（NVIDIA, 2026a）与 Slurm（Jette and Wickberg, 2023）等执行后端，让流水线机会性地利用空闲或部分可用的 GPU 容量。这提升了集群利用率，无须大块连续 GPU 预留即可实现持续数据处理。

**Agentic 作业编排。** 随着 AI agent 在工具使用与长时程执行方面能力不断增强，SILA 通过对 agent 友好的运维接口暴露大规模整理工作流，包括可复用技能、命令行接口（CLI）与结构化作业元数据。长时间运行的编排 agent 周期性地监控整理作业、检查日志与执行元数据、重启失败的阶段并自动协调运维恢复。通过这一持续监控循环，agent 可以跟踪流水线进度、识别停滞或不健康的 worker、核验数据集覆盖、在新模型或过滤标准引入时触发增量重算，并在分布式作业演化过程中就故障、恢复与执行状态通知工程师。

这些设计选择共同显著提升了大规模整理的效率。通过消除昂贵的启动期表 join，并用 fragment 级发现与协调取代随机化工作选取，SILA 将作业启动延迟从 30-60 分钟降至约 5 分钟（视阶段与模型配置而定）。结合分阶段执行、checkpoint 与集群利用率改善，新基础设施相对旧架构实现了 10× 吞吐量提升。在生产高峰期，单个 SILA 阶段每天处理数十亿行级标注，把大规模 caption 与整理活动从月级操作缩短为周级迭代周期。

除提升可扩展性与吞吐量之外，SILA 还把大量运维复杂性隐藏在以数据集为中心的接口之后，从而简化流水线开发。流水线作者只需声明其消费的输入列与产出的输出字段，框架便负责模式注册、列创建、fragment 发现、工作协调、checkpoint，以及将结果提交回共享数据集。于是，新增 caption、打分、打标或过滤阶段不再需要创建新存储表、编写同步逻辑或手工协调分布式 worker。研究者只需增量地添加新的带类型列、复用先前计算好的输出，并仅对缺失必需字段的样本重算即可持续迭代。

#### 5.1.2 嵌入存储与语义检索（Embedding Storage and Semantic Retrieval）

语义检索工作负载要求在数十亿条多模态数据上同时进行向量相似度搜索与元数据感知过滤。在旧架构中，高维嵌入直接存于 SQL 表会显著膨胀表体积，增加 join、扫描与运维查询的 I/O 开销。因此嵌入被导出到独立的向量数据库，而用于前过滤、后过滤与结果解读的元数据仍留在关系型存储中。然而，嵌入、元数据与过滤标准在整理期间持续演化：只要引入新的嵌入模型、元数据字段或搜索过滤器，就得在两套系统之间频繁同步与迁移。

SILA 转而把嵌入直接连同样本元数据一起存储在 Lance 中，使 LanceDB 能在主数据集上构建向量索引，无须单独的向量数据库（LanceDB, 2026）。由于嵌入存于 Lance 数据文件而非内联在关系行中，大嵌入载荷不会膨胀元数据表或拖慢运维查询。通过把嵌入、元数据与向量索引共置于同一存储层，SILA 可直接在整理后的数据集上支持语义检索、聚类与去重，同时保持搜索结果与最新整理状态一致。

在生产环境中，SILA 在一个覆盖数百亿行的 4096 维嵌入列上执行语义检索、聚类与去重，使用带余弦相似度的 LanceDB IVF_PQ 索引。部署的 Approximate Nearest Neighbor（ANN，近似最近邻）配置采用 64K 个 IVF 分区，并配合 PQ 压缩嵌入，以高效支撑十亿级检索工作负载。由于向量索引直接构建于主 Lance 数据集之上，语义检索与维护最新整理元数据和过滤状态的同一存储层上运作。这使得元数据感知过滤、最近邻检索与下游数据集分析能够与持续演化的嵌入、标注和整理输出保持同步，而无须在独立的向量系统与元数据系统之间做同步。

#### 5.1.3 数据集可视化、检查与调试（Dataset Visualization, Inspection, and Debugging）

在生产规模下，数据整理不仅要可扩展，还要可观测：研究者需要理解流水线覆盖情况、跟踪整理输出随时间的演化，并诊断单个样本为何通过或不通过质量标准。因此 SILA 将可视化、检查与调试视为数据基础设施的一等组件。其工具直接在 Lance 表上运作，将汇总级流水线进度、有代表性的开发子集、样本级检查与下游分析视图连接在同一共享整理基底中。

- **开发与流水线验证。** SILA 提供工具，从生产数据集构造小型开发用 Lance 表，同时保留全量语料的模式与有代表性的运维特征。由于这些开发表与生产数据高度一致，同一流水线可在两种环境中不加修改地运行，使研究者在启动大规模生产作业之前即可验证正确性与执行行为。
- **数据集检查与进度分析。** 为支撑大规模整理监控，SILA 直接在 Lance 表上暴露汇总进度分析器与交互式检查工具。fragment 级元数据用于估计逐列覆盖与流水线完成度，而无需全表扫描；交互式查看器允许研究者采样行、渲染媒体，并检查相关联的 caption、分数、标注与模式元数据。由于 Lance 支持高效的行级随机访问，这些检查工作流可直接作用于主整理表，避免了传统 Parquet 数据湖中常见的昂贵扫描与受限的行级检索模式。这使研究者能在同一数据集内从流水线级进度监控迅速下钻到样本级调试。
- **分析查询集成。** 对于大型分析负载，SILA 支持在线分析处理（OLAP）查询，用于对整理后的语料进行大规模聚合、报表与仪表盘展示。这些查询更易表达，因为 SILA 将每个样本及其整理信号存放在一张宽 Lance 表中：caption、标签、分数、嵌入、过滤决策与处理状态都可以从单一逻辑数据集中选取与过滤，而无须跨多条流水线专属表重建。选定相关列与队列后，分析后端即可计算覆盖报告、质量仪表盘、数据集审计与训练集分析所需的聚合。SILA 将 Lance 表保留为整理状态、媒体、元数据、嵌入、向量索引与行级检查的事实来源，而把下游分析执行视为一种部署选择。实践中，SILA 可扫描权威 Lance 表物化出可查询的快照或投影（包括 Parquet 文件，Le Dem, 2013），并使用可用的计算后端（如 Databricks、Spark 集群（Zaharia et al., 2016）或 Slurm 支撑的批处理作业）执行 OLAP 负载。

贯穿处理、检索与检查，SILA 闭合了定义 Cosmos 3 数据基础设施的三大目标的循环：将原始多模态语料转化为可训练样本、为语义检索与去重加以组织，并在整个整理生命周期内保持可检查。通过在单一 Lance 支撑的基底中统一资产、整理信号、嵌入、向量索引与执行状态，SILA 把数据整理从一连串一次性预处理作业转变为持续演进的生产工作流。新模型与质量标准可以增量应用；分布式富集阶段可以在共享的异构集群上恢复并扩展；研究者可以在语料级进度监控与样本级调试之间无缝切换。这一体化工作流使 Cosmos 3 训练语料能扩展至数百亿多模态候选，同时保持可检索、可审计与持续可改进。

### 5.2 训练基础设施（Training Infrastructure）

Cosmos 3 依托一个为扩展多模态基础模型训练而专门打造的基础设施平台。这一统一栈协调 Reasoner 与 Generator 训练的端到端生命周期，覆盖原始多模态样本接入、训练计算与持久 checkpoint，并围绕下述阶段组织：

- **数据加载器（Data loader）。** 以任意原生分辨率与宽高比例接入多模态样本——图像、视频、动作、音频、文本。它即时（on-the-fly）执行增强（如缩放、空间裁剪、颜色抖动与视频时间下采样），对文本条件做 tokenization，并将变长样本打包成批次。为隐藏 I/O 与预处理延迟，加载器在并行 worker 进程中异步运行，并通过锁页内存（pinned-memory）中转缓冲将批次预取到设备上。
- **分布式训练（Distributed training）。** 采用混合分片数据并行（Hybrid Sharded Data Parallelism, HSDP）与上下文并行（Context Parallelism, CP）的组合进行并行化，从而扩展到大模型尺寸与超长输入序列长度。HSDP 在每个副本组内分片优化器状态、梯度与模型参数，并在组间复制。CP 沿序列维度将数据分片到各设备，处理否则单卡显存无法容纳的超大上下文窗口。两种策略正交组合，并按实验动态配置，以针对目标模型尺寸、序列长度与集群拓扑进行优化。
- **训练循环（Training loop）。** 按 TorchTitan（Liang et al., 2024b）风格编排，训练循环执行标准的前向、反向、优化与学习率调度周期。它原生支持多种优化器（如 AdamW 及其融合变体）、调度器（如带 warm-up 的余弦、带 warm-up 的常数）与损失函数（Reasoner 文本用交叉熵损失，Generator 用 EDM 损失）。同时接入即时变分编码器（如 Wan2.2 VAE），整条流水线在原始多模态输入上端到端运行。该设计消除了离线的隐变量提取阶段，并确保增强、编码与训练在各次运行间保持步调一致。
- **Checkpoint 保存。** Checkpoint 按可配置节奏记录，并使用异步、脱离关键路径的持久化机制，防止磁盘与网络 I/O 阻塞训练循环。模型参数、优化器状态与 RNG/数据加载器状态在设备上快照，交接给后台写进程，在训练不中断继续的同时序列化到远端存储。

Reasoner 与 Generator 都以这一统一框架训练，共享同一个 trainer、并行架构、优化器、学习率调度器、tokenizer、数据加载器与监控工具。

#### 5.2.1 数据加载器（Data Loader）

数据加载器连接持久存储与训练循环：接入原始多模态训练数据、即时施加增强，并组成每个训练步消费的批次。在 Cosmos 3 中，数据加载器必须同时满足三项要求：

- **流水线饱和（Pipeline saturation）。** 必须异步流式供给批次，防止训练循环在数据 I/O 上停滞或阻塞。
- **分布式负载均衡（Distributed load balancing）。** 必须在分布式 rank 间发出均衡的批次，最大限度减少跨 rank 同步停滞，最大化整体 GPU 利用率。
- **分布保真（Distribution fidelity）。** 必须保证长期运行的模态与分辨率混合严格贴合配置的目标分布。

在传统 LLM 训练中，这三项要求都有成熟的解法。

- **流水线饱和** 通过调节 worker 数量、预取深度，并使用锁页内存中转缓冲来重叠主存到设备的传输与计算来实现。
- **负载均衡** 则轻而易举，因为每个样本贡献固定数量的 token；保持各 rank 样本数一致即可保证各 rank 统一的计算量与激活显存画像。

然而，Cosmos 3 让这套配方在全部三个维度上失效。由于其联合训练语料横跨高度异构的模态，单样本 token 数相差超过两个数量级，使得 token 量成为计算与显存开销的首要驱动。例如，单个 720p 两秒视频片段产生的 token 比几十条短文本 caption 加起来还多。在这种不对称负载下，给各 rank 分配相等的样本数会引入严重的系统性低效：(a) 固定批次形状造成大量 padding 浪费；(b) 当各 rank 的模态分配不同时产生严重的负载不均；(c) 大规模下极端的步时方差导致 NCCL 集合通信超时。

为应对这些挑战，Cosmos 3 数据加载器围绕四项协同机制构建：(i) token 预算打包序列——以 token 预算而非固定样本数约束每个 rank 的单步负载；(ii) 联合数据加载器——把各数据流加载器多路复用为单一统一训练批次；(iii) rank 同步的流选择——用全局播种的选择器使所有 rank 在每一步对齐到同一数据流；(iv) 前瞻打包（look-ahead packing）——提高 token 预算 T_max 的平均利用率。

**Token 预算打包序列。** 每个 rank 的单步负载不以固定样本数约束，而以严格的 token 预算 T_max 约束。加载器贪婪地把样本串接成单一打包序列——每个样本恰好贡献其序列化形式所需的 token，样本之间不插入 padding——直到追加下一个候选将超出 T_max 为止。通过消除跨样本 padding，该设计把单步计算成本约束为 T_max 的直接且可预测的函数，使硬件免受模态组合波动带来的执行方差影响。作为防御性的次级约束，单步样本数也封顶于 ⟨原文符号在文本抽取中丢失，待对照 PDF 复核：N_max⟩。

**联合数据加载器。** 每个模态、数据集或更细粒度的数据流都封装在自己的加载器中，配备私有预取缓冲以隐藏存储延迟。联合数据加载器（如 Fig. 12 所示）在这些各流加载器之间多路复用，每步组成单一统一训练批次，同时完整保留各流的缓冲、预取与可观测性。

> **Figure 12:（图 12）** 联合数据加载器总览。各流专用数据加载器为每个 rank 上的本地分流缓冲供数。在每个全局迭代，一个 rank 同步的选择器在分布式 rank 间选择同一个流 s。随后每个 rank 从其选定的本地缓冲中，在 token 与样本数预算下贪婪地打包样本组成批次 B(s)，并利用有限前瞻减少空闲 token 容量。⟨图内符号在文本抽取中丢失，以 PDF 原页为准⟩

**Rank 同步的流选择。** 基础模型训练通常同时从包含图像与多种空间分辨率视频的数据集中取样。各流的单样本 token 数相差数量级：例如视频样本往往比图像多 100× 以上 token，720p 视频又比 256p 视频多 10× 以上。若允许每个 rank 独立选流，在 FSDP 下会造成严重的负载不均——同一步内各 rank 的注意力 FLOPs（因其二次复杂度）差异悬殊。我们通过以迭代索引为键的全局播种选择器来选定活动流，确保所有 rank 在每一步都处理来自同一模态与分辨率桶的样本。这消除了跨 rank 的计算时间与激活显存方差，而确定性的、由种子导出的选择序列在 checkpoint 与重启之间可比特级精确复现。相比无同步基线，rank 同步流选择将端到端训练吞吐量提升 54%。

**前瞻打包。** 给定迭代 t 选定的流 s，联合数据加载器贪婪地构制本地批次：从流缓冲头部依次追加样本，直到下一候选超出 token 预算 T_max。然而纯贪心打包会在下一候选大到溢出、但缓冲深处还有更小可用样本时，留下相当比例的预算未被利用——这部分残余容量在功能上等价于 padding，与吞吐损失成正比。我们用有界前瞻策略解决：当某候选样本超出总 token 预算 T_max 时，该样本在当前配置下不可打包，将其丢弃（并记录警告）；当候选仅超出剩余预算、而批次已非空时，将该候选临时移入 look-aside（旁路）缓冲，加载器继续向流缓冲更深处扫描，寻找能填满残余容量的更小样本。

该机制如 Fig. 13 所示。示例中，样本 1 与 2 可放入当前批次；3 超出剩余预算，被转入旁路缓冲；加载器继续扫描，打包 4 与 6 等后续较小样本。迭代结束时，旁路缓冲中剩余的所有样本按原始到达顺序放回流缓冲头部，因此前瞻在不永久打乱流顺序的前提下减少 padding。为约束病态情形（如某流暂时被超大样本主导）的代价，每次迭代的连续前瞻尝试次数受可配置的每流上限约束。生产中我们取上限为十；超过该值后，空闲容量的额外缩减微乎其微，而旁路缓冲大小（及其显存占用）却持续增长。总体而言，前瞻打包将有效序列长度相对基线提升 8%，带来相应的训练吞吐量改善。

> **Figure 13:（图 13）** 联合数据加载器中的前瞻打包。加载器从选定流贪婪扫描样本，将能放入剩余 token 预算的样本打包进当前 mini-batch（Mint）；超出预算的样本被临时放置到 lookaside 缓冲（Rose），让后续更小样本填充剩余容量。迭代结束时，被跳过的样本按原始到达顺序返回流缓冲头部，从而在跨迭代保持流顺序的同时减少 padding。⟨图内符号在文本抽取中丢失，以 PDF 原页为准⟩

**冷启动处理。** 我们若干数据流的首批延迟很高，主要来自 worker 进程派生、新打开分片的文件系统元数据缓存，以及流专属的反序列化预热。若这笔延迟在第一个训练步才支付，它会与该步的 NCCL 集合通信"赛跑"，极可能在最慢的 rank 上触发 watchdog（看门狗）超时——在大规模下尤其如此，因为此时起作用的是跨 rank 的最大值。为消除这一失效模式，联合数据加载器在构造期间执行显式的预热阶段：从每个流各取一个批次，把 worker 池、文件句柄与反序列化缓存完全预热，随后发出分布式 barrier 再把控制权交还训练循环。这保证每个 rank 在第一次前向之前都已支付冷启动成本，第一个迭代面对的是完全预热的流。

**可观测性与集成。** 每个迭代，联合数据加载器向训练侧监控回调发出结构化打包统计记录；回调跨分布式组聚合各 rank 记录并将结果记入 Weights & Biases。上报指标包括：各流实测采样比例（与配置目标混合对比）、每迭代打包样本数、各流缓冲占用率与等待时间、前瞻饱和率，以及每迭代 token 预算利用率。这些指标暴露那些最可能在大规模训练中"不崩溃但悄悄劣化"的失效模式，使此类问题在发生数分钟内即出现在训练仪表盘上，而不是日后从模型行为中倒推发现。

#### 5.2.2 注意力实现（Attention Implementation）

如第 2.3.1 节所述，Cosmos 3 的 Mixture-of-Transformers 架构要求两种迥异的注意力模式在同一次前向中并存：Reasoner 通路仅对 Reasoner token 施因果注意力；Generator 通路则对 Reasoner 与 Generator token 的拼接施双向注意力，使每个 Generator token 能以完整上下文为条件。用 FlexAttention 这类通用算子朴素地表达这些异构掩码模式虽结果正确，但硬件利用率低：内核看不透掩码结构，在本应跳过的注意力块内仍执行了等价于 padding 的工作，从而降低 tensor-core 利用率并加剧内存带宽压力。

对此，我们协同设计了一种"双向扁平注意力"（two-way flat attention）机制，把跨通路掩码结构直接暴露给高性能变长注意力内核。设计如 Fig. 14 所示。计算被分解为两次独立的内核调用。第一次处理 Reasoner 通路，是仅作用于 Reasoner 查询、键、值的标准变长缩放点积注意力（SDPA）（PyTorch Contributors, 2026b）带因果掩码调用。第二次处理 Generator 通路：要求同一样本内 Reasoner 与 Generator 的 key/value 流对所有 Generator 查询可见，但在打包批次内各样本之间严格隔离。我们通过在样本粒度上把两条 token 流按下式扁平交错来实现：

$$[R_0, G_0, R_1, G_1, \ldots, R_{n}, G_{n}]$$

其中 ⟨原文符号在文本抽取中丢失，待对照 PDF 复核：R_i 与 G_i 分别表示样本 i 的 Reasoner 与 Generator key/value token⟩。每个 Generator 查询在其自身样本的 [R_i, G_i] 块上双向注意。这一表述以每层两次变长内核启动表达全部跨通路注意力，在同一打包表示中同时支持因果与双向掩码，消除固定长度实现固有的 padding 开销，相对基于 FlexAttention 的基线，为 Cosmos3-Nano 带来 22% 的端到端训练吞吐提升。

> **Figure 14:（图 14）** 双向扁平注意力。每条通路实现为单次变长 SDPA 调用。(a) Reasoner 通路在打包的 Reasoner token 上使用标准因果 varlen 调用，产生块对角因果掩码。(b) Generator 通路将 Generator 查询与交错 key/value 流 [R₀,G₀,R₁,G₁,…,Rₙ,Gₙ] 分开打包。所得掩码是块对角的，且每块内为矩形，使每个 Generator 查询在其自身样本的 [Rᵢ,Gᵢ] 上下文上双向注意而不越出样本边界。示例使用三个打包样本，(|Rᵢ|,|Gᵢ|) = (3, 2), (2, 3), (4, 1)。⟨图内符号在文本抽取中丢失，以 PDF 原页为准⟩

变长注意力后端按平台选择，以匹配目标硬件上性能最佳且经过数值验证的实现。在 Hopper 级 GPU（H100、H200）上，我们使用 FlashAttention-3（Shah et al., 2024），它利用 Hopper 架构的 WGMMA 指令与基于 TMA 的异步数据移动，提供接近峰值的注意力吞吐。在 Blackwell 级 GPU（GB200）上，我们使用 NATTEN（Hassani et al., 2023），其变长内核基于 CUTLASS 模板库构建，专门为 Blackwell（SM100/SM103）第五代 tensor core 与更新的内存层级调优。两个后端经由统一的分派接口访问，因此内核选择对训练栈其余部分透明，并可随新后端成熟而重新评估。

#### 5.2.3 分布式训练（Distributed Training）

Cosmos 3 的 Reasoner 与 Generator 分别使用一套分布式训练栈训练，该栈将混合分片数据并行（HSDP）与上下文并行（CP）相结合。HSDP 在每个副本组内分片模型参数、梯度与优化器状态，并在组间复制，以少量组内通信换取在单卡显存预算有限的商用 GPU 上训练数十亿参数模型所需的显存余量。CP 针对另一类瓶颈：单序列激活显存——它随上下文长度线性增长，否则会对可训练序列长度形成硬性上限。两种策略正交组合，(HSDP 度, CP 度) 配置按实验选定，以匹配目标模型尺寸、序列长度与集群拓扑。

**经由 Ulysses 方案的上下文并行。** 对 CP，我们采用 Ulysses 方案（Jacobs et al., 2023）：在注意力之外沿 token 维将输入序列切分到 CP rank 设备上，并在每次注意力层中用两次 all-to-all 集合通信切换分片轴。第一次集合通信把 Q/K/V 激活从序列维重新分布到注意力头维，使每个 rank 持有一组不相交 head 的完整序列，从而可在本地执行注意力而无需进一步跨 rank 通信；第二次集合通信把布局恢复到注意力输出上的原序列分片。

该方案与序列打包（见 5.2.1 节）及双向注意力机制集成得很干净：为双向注意力操作而对 Reasoner 与 Generator key/value 流的扁平交错被推迟到 head 轴重分布之后进行——此时每个 rank 已持有其负责 head 的完整序列，可在本地完成拼接。因此同一套变长注意力内核在 CP 中原样复用，无须 CP 专属内核变体。此实现支持的最大 CP 度受限于模型中的查询头数——Cosmos3-Nano 为 32，Cosmos3-Super 为 64——鉴于 Cosmos 3 的目标上下文长度与单卡显存预算，我们在实践中发现这一限制并不构成约束。

**为何不用 ring attention？** 我们考虑过以 ring attention 实现 CP 的替代方案，但在我们的设定下发现其吸引力明显不足。Ring attention 需要先把交错排布的 Reasoner 与 Generator token 物化为单一打包序列，再跨 CP rank 分片，以便向环形调度暴露连续的 K/V 流。这排除了 Ulysses 天然允许的"两条通路独立分片"，并使旋转环形调度下逐样本双向/因果掩码的构造复杂化。再加上 all-to-all 在 NVLink 互联节点上的带宽优势，这些因素促使我们选择 Ulysses 作为 Cosmos 3 的 CP 策略。

#### 5.2.4 选择性激活重计算（Selective Activation Checkpointing）

计算 Transformer 的反向传播需要前向产生的中间激活可用，但在 Cosmos 3 的目标模型规模与上下文长度下，同时物化全部激活的显存代价不可承受。标准缓解手段是激活 checkpointing（activation checkpointing，即激活重计算）（Chen et al., 2016）：前向只存储一小集"锚点"激活而丢弃其余，被丢弃的张量在反向期间从最近的已存锚点重跑相应前分子图来重算。默认策略只保存每个 Transformer 块的输入，块内一切按需重算；这把激活显存降到最低，却在反向引入一次额外出前向，使单步 FLOPs 增大约 33%，端到端训练吞吐相应下降。

为在激活显存预算内降低这一重分开销，我们应用选择性激活 checkpointing（Selective Activation Checkpointing, SAC）：把一小部分精选中间张量额外驻留内存而不重算。选择遵循一条简单的成本-收益启发式：按 FLOPs/字节内存比——即每提交一字节激活显存所省下的重算代价——对候选操作排序，优先物化比值最高者，直至激活显存预算耗尽。对 Cosmos 3 而言，注意力输出是该策略的最大受益者：注意力的重算开销巨大，因为成本随序列长度二次增长；而注意力输出张量本身相对较小（随序列长度与隐藏维线性），因此它是 FLOPs/内存比最高的操作。用户还可通过对操作名的正则表达式模式配置自定义保存集合，我们在残余激活显存余量允许时用它保留少量次级张量。

实测表明，对 Cosmos3-Nano 采用"物化注意力输出"的 SAC，在单批次 token 预算 74,000 下带来 13% 的端到端训练吞吐提升，且数值结果不变。

#### 5.2.5 Transformer 块的 Torch Compile（Torch Compile for Transformer Blocks）

我们在整张训练图上应用 torch.compile，设 fullgraph=True 与 dynamic=True。fullgraph 模式消除 CPU 开销并启用算子融合；dynamic=True 处理混合模态批次带来的可变序列长度——例如 Generator 通路 token 在各迭代间远长于图像批次。Torch compile 为 Cosmos3-Nano Generator 训练带来 41% 的吞吐提升。

#### 5.2.6 视频分词器（Video Tokenizer）

Cosmos 3 训练要求解码后的视频帧由视频 VAE 即时 tokenize 为隐变量表示：我们的配置使用 Wan2.2（Wan et al., 2025b）。初版实现中，我们观察到该 tokenizer 在每个训练步中占据不成比例的份额——对较小的 Cosmos3-Edge 与 Cosmos3-Nano 模型甚至主导整个前向。在这类模型中，Transformer 计算足够小，VAE 无法被其余步骤摊薄。由于 tokenizer 位于数据加载器与训练循环之间的关键路径上，它引入的任何延迟都直接侵蚀训练吞吐。为此我们实现了一系列针对性优化，合起来显著降低了 tokenizer 的墙钟时间贡献。

**分块编码（Chunked encoding）。** Wan2.2 因果 tokenizer 先编码一个 1 帧的"prime"块，随后每个隐变量块对应 4 个像素帧；默认的每次调用粒度为一个隐变量块（即 prime 之后每次 4 帧）。这一默认设置使 GPU 在训练所用空间分辨率下严重欠利用，因为每次内核启动的工作量太小，无法让 tensor core 饱和。我们改为按可配置的每调用像素帧数调用编码器，以更多激活显存换取每次启动更高的算术强度。最优块大小取决于分辨率：空间分辨率越高，每帧本身已消耗大量显存，触发 OOM 前每次可容纳的帧数越少；分辨率越低，可行且有益的块可以大得多。我们在训练硬件上经验确定了以下工作点：256p 用 68 帧，480p 用 24 帧，720p 用 12 帧。这些配置将编码器推到 roofline 曲线的计算受限一侧，同时远低于单卡显存预算，贡献了单步加速的主体。

**提前编译（Ahead-of-time compilation）。** 在分块编码之上，我们对 tokenizer 使用 torch.compile：通过融合逐点（pointwise）操作并为编码器的卷积与注意力块选择优化内核调度，额外将编码延迟降低 52%。吞吐最大化需要静态输入形状，因此编码器按其可能被调用的每种形状分别编译。Cosmos 3 训练跨三种空间分辨率（256p、480p、720p）、每种分辨率五种宽高比；在每个（分辨率, 宽高比）组合内，因果 tokenizer 以两种模式调用：prime 块编码，以及 cache 大小为 1 和 2 的分块编码。这产生 3 × 5 × 3 = 45 张必须在训练开始前编译好的独立计算图。在每个 rank 上串行编译全部 45 张图会使训练器启动时间增加约 15 分钟。

为消除这一开销，我们使用 AOTInductor（PyTorch Contributors, 2026a）把编译跨数据并行 rank 分片，如 Fig. 15 所示。AOTInductor 执行提前编译，并将所得内核与宿主代码序列化到磁盘。只要有至少 45 个 rank（我们所有训练配置都满足），每个 rank 恰好编译一张图；编译产物写入共享文件系统，随后每个 rank 从磁盘加载全部 45 张图。这将预热开销降到一分钟以内。为在静态形状编译下容纳任意帧数的视频，每个输入片段在编码前先右填充到所配置编码块大小的下一个整数倍，所得隐变量张量在送入模型前沿时间轴裁剪到精确的预期序列长度。

**特化到已知帧数。** 对于每片段帧数固定且可先验得知的数据集——例如机器人动作数据集，其中每条 episode 贡献等长片段——我们将编译特化到运行时实际出现的精确张量形状，绕过一般情形的"填充-再裁剪"回退路径。这消除了填充尾部的计算，省去相应的隐变量裁剪步骤，在此类数据集上带来小幅但稳定的额外吞吐提升。

> **Figure 15:（图 15）** Wan2.2 tokenizer 的分片提前编译。由 {3 种分辨率} × {5 种宽高比} × {3 种 tokenizer 调用模式} 产生的 45 张静态形状图被划分到各 rank；每个 rank 对其分配的图执行编译，将编译产物写入共享文件系统，并在训练开始前加载全部产物。预热时间从串行约 15 分钟降至分片后不到 1 分钟。

#### 5.2.7 Checkpoint（Checkpointing）

为消除保存导致的停顿，checkpoint 与训练完全重叠。沿用 Torchtitan（Liang et al., 2024b）的做法，checkpoint 写入经由一个专用 Gloo 进程组路由，而不是承载训练集合通信的 NCCL 通信器，从而将 I/O 流量与 GPU 侧通信隔离。这一异步设计隐藏了对象存储高度波动的写入延迟，几乎消除了全部保存开销，代价是主机内存的小幅增加。Tab. 7 量化了所得收益：相对于 30 分钟间隔的同步 checkpoint，异步 checkpoint 使 Cosmos3-Nano 端到端训练时间减少 4%，Cosmos3-Super 减少 9%。

**异步保存机制。** 构造时，checkpointer 以 spawn 启动方法派生一个长生命周期子进程，通过 multiprocessing 队列与之通信。子进程加入 Gloo 进程组并执行构制保存计划所需的 CPU 侧归约，让 GPU 继续用于训练。它随后阻塞在接收队列上，直到收到 checkpoint 保存请求或终止哨兵（sentinel）。

**保存计划记忆化。** 为进一步降低开销，checkpoint 保存计划在第一次保存时计算，并在后续保存中复用。这可行是因为保存计划是 state-dict 拓扑的确定性函数。复用计划避免了跨 rank 的重复元数据通信，将 checkpoint 开销降低约 60%，进一步减少异步 checkpoint 成为训练瓶颈的可能。

**针对对象存储的优化。** Checkpoint 保存期间，每个 rank 将自身 state-dict 的本地分片写入对象存储。可能在多个 rank 上出现的复制（replicated）张量在写入前去重。在默认轮转（round-robin）分配下，复制张量可能由不同 rank 写入，导致加载时每个 rank 必须读取所有 checkpoint 文件才能恢复复制状态。这引入显著开销，因为即便只需一小部分内容也必须整文件加载。为降低该开销，我们设置 dedup_to_lowest_rank = True，把复制张量只存入相应 submesh 中编号最小的 rank（通常为 rank 0）。加载时每个 rank 只需读取自己的分片与 rank-0 分片。这大幅缩短 checkpoint 加载时间，对包含许多小型复制张量的优化器 state-dict 尤其明显。

**随机状态恢复。** 训练器以 rank 感知方式恢复随机数生成器（RNG）状态。由于 RNG 状态以 rank 为键，恢复作业先检查 checkpoint 元数据中自己 rank 对应的键，仅当存在时才请求该状态。这保持与早于 rank 键控 RNG 格式的旧 checkpoint 的兼容性。若 rank 专属键不存在，该 rank 保留其当前 RNG 状态。

### 5.3 服务基础设施（Serving Infrastructure）

Cosmos 3 与多个生产级服务框架集成，以支撑广泛的部署场景。Reasoner 由 TensorRT-LLM（NVIDIA Corporation, 2026）与 vLLM（Kwon et al., 2023）支持，二者通过分页 KV-cache 管理、连续批处理（continuous batching）与融合注意力内核，提供高度优化的自回归解码。Generator 推理由 vLLM-Omni（vLLM 面向扩散生成的多模态扩展）（Yin et al., 2026）支持，它在峰值吞吐与多租户调度效率之间提供互补的权衡。除这些生产后端外，我们还提供原生 PyTorch 参考实现，优先可读性与可修改性：它既是推理算法的忠实规范，也是下游适配、研究性扩展与接入定制应用流水线的起点。

#### 5.3.1 原生 PyTorch（Plain PyTorch）

原生 PyTorch 服务路径在 eager 模式 PyTorch 中直接执行模型及其外围推理流程——不依赖专门的服务运行时——其设计尽可能忠实镜像训练期计算。该路径负责完整的端到端推理工作流，包含下述阶段：

- **输入准备。** 解析文本提示词，加载图像、视频或动作条件，构造模型消费的模态专属条件字典，并组装相应输入张量与元数据。
- **自回归循环。** 在 Cosmos 3 Reasoner 中，输出 token 以自回归方式产生，每步以先前生成的 token 及条件上下文的已缓存 key/value 状态为条件。
- **扩散循环。** 在 Cosmos 3 Generator 中，PyTorch 路径构制时间步调度，在每步调用去噪器，施加 classifier-free guidance（CFG），按采样器更新隐变量状态，并管理去噪过程外围的请求级控制流。
- **解码与后处理。** 去噪完成后，所得隐变量表示被解码到目标模态——文本、图像、视频、音频或动作——按需后处理，并通过服务接口返回给调用方。

由于原生 PyTorch 后端保留模型原始 PyTorch 结构，它是落地新模型特性、采样器修改、KV-cache 与激活缓存策略以及调试仪表的首要目标。新能力先在此后端验证，随后才移植到生产运行时（TensorRT-LLM 与 vLLM），确保参考实现始终是推理算法的权威规范。PyTorch 后端暴露以下特性与优化。

**带 CUDA Graphs 的 Torch compile。** 由于 PyTorch 原生推理路径将请求编排与采样逻辑留在 Python 中，服务的一个主要瓶颈是反复去噪步中的宿主侧内核启动开销。因此我们用 torch.compile 与 CUDA graph 重放来优化 PyTorch 路径。CUDA graph 优化以 Transformer 层为粒度实现，捕获重复的 Transformer 块执行。每个块以 reduce-overhead 模式用 torch.compile 编译，使 PyTorch Inductor 将其降级并在张量形状与内存布局兼容时改用 CUDA graph 重放。外层推理循环保持普通 PyTorch：提示词处理、时间步调度、采样器更新、CFG 编排、解码都不进入被捕获的图。图内只包含计算量大且高频重复的逐层计算，动态服务逻辑留在图外。CUDA Graphs 的收益在 T2I 类生成上最明显——生成负载较短、内核较小，使得 CPU 启动开销占端到端延迟比例更高。CUDA Graphs 为 T2I 生成在不同硬件后端上带来 30% 到 60% 的加速。

**分布式推理。** 推理时我们采用上下文并行（CP）以支撑超出单 GPU 显存约束的生成。我们保留训练期使用的 Ulysses 方案（Jacobs et al., 2023），确保两种情形一致。除支持长上下文推理外，CP 还通过把前向分散到多块 GPU 上充当一种降延迟机制；即便在单卡显存足以容纳完整上下文的场景，这一收益依然成立，使 CP 成为通用的推理加速工具。

除上下文并行外，我们还利用 CFG 并行进一步降低端到端推理延迟。带 CFG 的扩散采样在每个去噪步需要两次模型前向——一次以输入提示词为条件，一次无条件——两者的噪声预测线性组合得到引导更新。由于条件与无条件两次前向作用于独立输入，且只需每步同步一次形成引导预测，它们是跨两块 GPU 并行化的理想对象。实践中我们并发派发条件与非条件批次，只做一次轻量的点对点交换合并两个预测，然后推进采样器。这几乎将单步延迟减半，并与上下文并行干净组合，在多 GPU 节点上提供乘性延迟缩减。

**Reasoner 塔缓存。** 对 text-to-image（T2I）、text-to-video（T2V）、image-to-video（I2V）、video-to-video（V2V）等任务，Reasoner 塔的条件输入——文本提示词，以及适用时的条件图像或视频——在整条采样轨迹期间固定不变。因此 Reasoner 的输出在各扩散步间不变，只依赖于条件，不依赖当前噪声水平或部分去噪样本。我们利用这一性质：在推理开始时计算一次 Reasoner 前向，并缓存其输出以供后续所有去噪步复用。由于缓存的激活与逐步重算在数学上完全相同，该优化在不影响任何生成质量的前提下大幅降低单步延迟。

**批处理。** 把多个样本批量并入单次前向可进一步提升推理吞吐，将每步固定开销（内核启动、权重读取、集合通信）摊到更多有效工作上。我们的推理批处理器复用为训练开发的变长序列打包机制：不是把较短序列 padding 到统一长度（那会把计算与显存浪费在 padding token 上），而是把异构形状的样本拼接成单一打包张量，并向注意力及其他形状敏感算子提供相应的累积序列长度元数据。用户指定两种预算模式之一：总 token 预算（批次允许的最大 token 数）或固定样本数。给定所选预算，批处理器贪婪地打包进入的样本直至预算耗尽，同时遵守每设备显存约束。这一设计提升吞吐导向部署（如离线语料生成与大规模评估）的 GPU 利用率，但在延迟受限场景（如机器人工作负载）中没有收益——那里单个样本必须独立处理；此时批处理器配置样本数为 1，实际上被禁用。

**配合提示词上采样的生成。** 推理还支持提示词上采样（prompt upsampling）模式（详见第 6.3.2 节）：由 Reasoner 把简短的自由式用户提示词扩展为更丰富、结构化的 JSON 期望输出描述（涵盖场景构成、主体属性、相机与运动规格、光照与风格等）。上采样后的描述由 Reasoner 自回归生成，随后作为附加条件输入连同用户提供的任何图像、视频或动作条件一起送入 Generator，合成最终输出。该流水线有两大用途：把细致提示词工程的负担从终端用户转移给模型本身，稳定改善下游生成质量；并在单次推理调用中贯通检验 Reasoner 与 Generator 两条通路的全模态端到端能力——证明两条通路可以被无缝组合，从最简用户规格产出高保真多模态输出。

**吞吐 vs 延迟的服务考量。** 推理工作负载一般优化两个相互竞争目标之一：吞吐或延迟。批量推理——对固定输入语料生成大批输出——通常优化吞吐，因为关心的是端到端墙钟时间与总成本。相反，延迟敏感应用——例如机器人，动作必须从特定起始上下文产生且有严格的每步时限——优先考虑响应速度，其指标是首 token 时间（或首动作时间）与单步延迟。上述优化对不同情形的侧重不同：分布式推理（上下文并行与 CFG 并行）主要通过把单个请求跨多设备并行化来降低延迟，而批处理主要通过跨多个并发请求摊薄每步开销来提升吞吐。其余优化——torch compile 与 reasoner 输出缓存——对两种情形同时有益。

#### 5.3.2 Reasoner 的推理框架：vLLM 与 TensorRT-LLM（Inference Frameworks for Reasoner: vLLM and TensorRT-LLM）

由于 Nano 与 Super Reasoner 基于 Qwen3-VL（Bai et al., 2025b）骨干构建，它们在 vLLM 与 TensorRT-LLM 中的集成复用两个框架已有的上游 Qwen3-VL 支持。这让我们开箱即用地继承两个后端本已为 Qwen3-VL 家族提供的优化注意力内核、分页 KV-cache 管理、连续批处理与多模态输入处理，只需极少的配置改动即可把 Cosmos 3 模型权重与 tokenizer 绑定到既有执行路径。

相比之下，Edge Reasoner 构建在自定义 Nemotron 骨干（NVIDIA, 2025）之上，vLLM 并不原生支持。因此我们遵循 vLLM 模型贡献者规范实现了专门集成。该集成的结构支持向上游游说合入（upstreamable），以降低未来维护成本并方便社区贡献。

#### 5.3.3 Generator 的推理框架：vLLM-Omni（Inference Frameworks for Generator: vLLM-Omni）

Cosmos 3 Generator 集成进 vLLM-Omni，以利用其为扩散式多模态生成优化的服务栈。该集成把 Cosmos 3 Generator 实现为一等公民的 vLLM-Omni 模型，支持完整的 Generator 模态集合，包括图像、视频、音频与以动作为条件的生成。它遵循 vLLM-Omni 框架的模型贡献者规范与代码风格，使实现与框架既有的调度、分布式执行、显存削减与量化特性兼容。

这一集成对 Generator 服务尤为重要，因为扩散式生成需要对大规模图像、视频或多模态 token 序列进行大量重复的 Transformer 求值。vLLM-Omni 后端因而聚焦于降低单步延迟、削减峰值显存占用并提升吞吐，同时保持生成质量。Cosmos 3 Generator 集成支持以下 vLLM-Omni 特性：

- **Cache-DiT。** 一种免训练加速方法，在相邻去噪步之间复用缓存的 Transformer 块输出，从而跳过冗余计算，对生成质量影响可忽略。
- **Ulysses 上下文并行。** 一种上下文并行执行方案，把长图像与视频 token 序列分片到多块 GPU，使用 all-to-all 注意力通信降低单设备显存占用并改善延迟。
- **CFG-Parallel。** 一种针对 classifier-free guidance 的并行策略，把条件与非条件前向分发到不同 GPU rank；两个预测在每个去噪步同步一次形成引导更新，降低 CFG 采样的延迟。
- **HSDP。** 一种显存高效的分布式推理模式，使用 FSDP2 将 Transformer 权重分片到多块 GPU，并在前向期间按需聚集参数，降低大型 Generator 模型的峰值显存需求。
- **CPU offload。** 一种逐层卸载机制，在推理期间于 CPU 与 GPU 显存间搬运模型参数，用额外数据传输开销换取大幅降低的峰值 GPU 显存占用。
- **VAE-Patch-Parallel。** 一种并行 VAE 执行模式，把隐变量或像素张量按空间分块切分，在多个 rank 上编码或解码，同时降低单设备显存消耗与 VAE 延迟。
- **量化（Quantization）。** 一条动态 FP8 量化路径，降低主要计算操作的精度以减少推理延迟与峰值显存占用，同时保持可接受的生成质量。

这些特性共同使 Cosmos 3 Generator 能够从显存受限的单 GPU 部署扩展到高吞吐多 GPU 服务。Cache-DiT 与量化降低重复去噪计算的成本；上下文并行与 CFG-Parallel 通过跨 GPU 分发单个请求改善延迟；HSDP、CPU offload 与 VAE-Patch-Parallel 则为高分辨率或长时长生成任务减轻显存压力。Figure 16 汇总了 Cosmos 3 的服务性能：比较不同硬件后端上的单 GPU 运行，以及 B200 上的多 GPU 运行。评估在 PyTorch-OSS 与 vLLM-Omni 两个框架下进行。

### 5.4 基准测试基础设施（Benchmark Infrastructure）

Cosmos 基准系统管理 Cosmos 模型的评估作业，并同时存储生成产物与评估结果。一个编排层在 Lepton 或 Slurm 集群上调度生成、打分与端点评估作业，并跟踪每个阶段的执行状态。对每次运行，系统记录元数据，包括模型 checkpoint、代码版本、所选基准、生成设置、基准专属参数与相关数据集。这些记录共同建立了每个上报分数与产出它的精确模型权重、输入、参数配置及评估代码之间的完整可追溯性。

系统支持第 6 节描述的异构基准套件，而不要求所有基准共享同一实现。基准评估生成视频、音频、动作轨迹以及 reasoner 模型的文本回答，覆盖多种准则，包括视觉保真度、音频质量、音画同步、提示词与控制遵循度、动作或轨迹精度、任务完成度、物理合理性与推理正确性。评估器既集成开源库与公开基准套件，也包括为 Cosmos 专门开发的自定义评估器。打分方法涵盖基于参考的误差指标、感知与时间一致性度量、音视频对齐指标、基于 VLM 的评审（judge）、人工标注，以及精确匹配或数值答案评估。

对 Generator 评估，基准测试分为生成与打分两个阶段。生成作业使用 PyTorch 推理流水线或第 5.3 节所述某个服务框架执行模型，并把生成输出写入对象存储。打分作业随后消费这些已存产物，计算逐样本与聚合指标，并将结果连同运行元数据一并记录。这一解耦设计允许用新指标或新评估器对输出重新打分，而无须重跑生成。

对 Reasoner 评估，我们使用 VLMEvalKit（Duan et al., 2024）框架配合 vLLM。这些作业向已部署的模型端点发送提示词与多模态输入，处理模型响应，并记录基准分数与相关元数据。

评估分数与运行元数据存储在关系型数据库中，生成产物存储在对象存储中。人工评估标注与被评估产物及问题集一并存储，聚合人工评估结果与自动化指标并行跟踪。一个基准门户通过仪表盘、排行榜、样例级检查工具以及模型对模型、checkpoint 对 checkpoint 的比较，向这些记录提供访问。
